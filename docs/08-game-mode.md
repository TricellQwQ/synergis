# 08 — Игровой режим (game mode): что это даёт и чего стоит

Решение: **Synergis делается отдельным игровым режимом Noita**, а не обычным модом,
подмешивающимся к стандартному забегу. Этот документ — проверенные последствия.

**Поправка к моему прежнему совету.** В первых версиях `docs/00` я писал, что свой
game mode «конфликтует» с EW, и рекомендовал `is_game_mode="0"`. Это была перестраховка.
Проверка по исходникам показала: **конфликта нет, EW сам предусматривает игровые режимы.**
Подробности в §2. Прежняя формулировка исправлена.

---

## 1. Сначала: два разных «режима игры» с одинаковым названием

Это первое, что надо развести, иначе будет путаница в каждом обсуждении.

| | **Режим Noita** | **GameMode в прокси EW** |
| --- | --- | --- |
| Где задаётся | `mod.xml` → `is_game_mode="1"` + `ui_newgame_*` | GUI `noita_proxy.exe` |
| Что выбирает | пункт в меню **New Game**, свои сейв-слоты, свои `magic_numbers` | модель здоровья: `SharedHealth` / `LocalHealth(Normal\|Alternate\|PermaDeath\|PvP)` |
| Как читать из Lua | `np.GetGameModeNr()`, `np.GetGameModeName(nr)` (NoitaPatcher) | `ctx.proxy_opt.pvp`, `ctx.proxy_opt.perma_death` и т.п. |
| Реализация | движок + твой `mod.xml` | Rust-enum в `noita-proxy/src/lib.rs:72` |

Они **независимы**: поставить в прокси «PvP» не создаёт режим Noita, а свой режим Noita
не меняет модель здоровья в прокси. Тебе, скорее всего, нужно и то и другое:
режим Noita — для идентичности, сейвов и генерации; опция прокси — для perma-death.

## 2. Проверено: режим совместим с прокси EW

Четыре факта из исходников, а не предположения.

**2.1. Прокси не диктует режим.** `noita-proxy/src/bookkeeping/noita_launcher.rs:57–65`:

```rust
let default_start_args = if cfg!(target_os = "windows") {
    let executable = game_exe_path.as_os_str().to_owned();
    Some(NoitaStartCmd {
        executable,
        args: Vec::new(),        // ← аргументов нет
        ...
```

На Windows прокси запускает просто `noita.exe` **без аргументов**. Значит режим выбирается
**игроком в меню New Game** — ровно так, как и задумано для `is_game_mode="1"`.

Если режим нужно форсировать, есть `--launch-cmd` (`noita-proxy/src/util/args.rs:12`),
и разработчики EW сами им пользуются — в `Justfile` есть
`--launch-cmd "wine noita.exe -gamemode 0"`. То есть `-gamemode N` — штатный способ.

**2.2. EW сверяет режимы между игроками.** `quant.ew/files/system/player_sync.lua:116–154`:

```lua
function rpc.check_gamemode(gamemode, seed, world_num, has_won)
    local mn = np.GetGameModeNr()
    local gm = np.GetGameModeName(mn)
    ...
    local not_fine = gamemode ~= gm
    ...
    if not_fine then
        GamePrint("Player: " .. ctx.rpc_player_data.name .. ", is on a different gamemode number then you")
```

Раз в 300 кадров EW сравнивает **имя** режима у себя и у собеседника и печатает
предупреждение при расхождении. Сравнение идёт **на равенство**, а не по списку
разрешённых значений — кастомный режим это не отвергает, а лишь требует, чтобы он был
одинаковым у всех. Заодно там сверяются сид (`StatsGetValue("world_seed")`) и
`ctx.proxy_opt.world_num`.

**2.3. EW знает про слоты сохранения.** `player_sync.lua` синхронизирует
`player_fns.get_current_slot(ctx.my_player)` как `current_slot`. То есть слот — известное
EW понятие, а не что-то, что ты ломаешь, включая `game_mode_supports_save_slots`.

**2.4. EW уже обходит грабли game mode-модов.** `player_sync.lua:119–127`: если имя режима
(`gamemode` или `gm`) равно `"save_slots_enabler"`, EW подменяет его на пустую строку и
трактует как «new run». То есть режим-мод, ломавший сверку, уже кто-то обошёл, и обход
встроен в EW.

## 3. Что даёт режим (аргументы в пользу твоего выбора)

1. **Своя витрина.** Отдельный пункт в New Game с именем, описанием и баннерами —
   это то, что отличает «режим» от «мода».
2. **Свои слоты сохранения** (`game_mode_supports_save_slots="1"`).
3. **Свои `magic_numbers` — главный технический выигрыш.** Режим — это отдельный режим,
   поэтому его константы генерации **не протекают в обычную игру**. Ты можешь задать
   свой `BIOME_MAP`, `DESIGN_PLAYER_START_POS_X/Y` и прочее. В обычном моде ты бы
   переопределял константы генерации **для всех забегов, включая ванильные** — это
   заметно хуже и по совместимости, и по отладке.
4. **Чистое включение/выключение.** Не нужны костыли вида `if ModSettingGet("...match_enabled")`:
   логика БР активна только когда выбран режим. Оговорка: `init.lua` мода исполняется
   в любом случае — гейтить логику надо самому, по `np.GetGameModeNr()` / имени режима.
5. **`GameIsModeFullyDeterministic()`** существует в API (`lua_api_documentation.txt`,
   строка 203) — у режимов есть понятие «полностью детерминированный». В мультиплеере это
   не праздный вопрос: **проверь, что возвращает твой режим**. Если детерминизм
   включается, это подсказка, что движок ведёт себя иначе (и, возможно, полезно для
   синхронизации). Не проверял — это твой тест.

### Варианты `magic_numbers` по слотам

Официальный пример `mods/daily_practice/` (тоже game mode) содержит 12 файлов:
`magic_numbers_01.xml … _06.xml` и `_01l … _06l`. Я их вычитал, вот что там внутри:

- `magic_numbers_0N.xml` → `BIOME_MAP=".../biome_map_0N.lua"` и
  `DESIGN_PLAYER_START_POS_X="160"`, `DESIGN_PLAYER_START_POS_Y=<Y Holy Mountain N>`
- `magic_numbers_0Nl.xml` → то же, но `X="-690"`, то есть **заход с левой стороны**
  (`l` = left), и `Y` на ~40 больше
- `biome_map_0N.lua` отличаются одной строкой: `parse_until_height(N)`

То есть это «практиковать daily run, начиная с Holy Mountain N, справа или слева».

**Честная неопределённость:** *каким именно правилом* движок выбирает
`magic_numbers_0N.xml` (по индексу слота? по номеру режима? по чему-то ещё) —
я не подтвердил по первоисточникам. Страница вики [Modding: mod.xml](https://noita.wiki.gg/wiki/Modding:_mod.xml)
описывает только `game_mode_supports_save_slots`, а в ванильном `data/` есть лишь
`magic_numbers.xml` и `magic_numbers_disable_debug.xml` — никаких `_0N`. Проверяется
эмпирически за пару минут: положи два варианта с разными `DESIGN_PLAYER_START_POS_Y`
и посмотри, где появляешься.

## 4. Чего это стоит (что придётся решить)

**4.1. Игрок обязан выбрать режим в меню.** Прокси этого не сделает. Значит в инструкции
для друзей это шаг №1, и расхождение режимов приведёт к сообщению
`"is on a different gamemode number then you"` — по нему и диагностировать.

**4.2. EW написан под режимы 0 и 2 (Daily Run).** Все проверки вида
`np.GetGameModeNr() == 2` молча уйдут в `else`:

- `player_tether.lua:23, 107, 291`
- `notplayer_ai.lua:1010, 1124`
- `player_sync.lua:117, 183, 199`

Для тебя это, скорее всего, именно то, что нужно (там костыли под Daily Run), но знай:
ты идёшь по непроторённой ветке, и странности в поведении EW надо сначала проверять
на «ванильном» режиме, прежде чем винить свой.

**4.3. Главный риск: жёстко прописанная геометрия мира в EW.** Это следствие того,
что ты выбираешь одновременно и режим, и кастомную генерацию. Если твой режим подменит
`BIOME_MAP` на компактную арену:

| Что | Устоит? |
| --- | --- |
| Всё, что считается от `BiomeMapGetSize()` — например `check_parallel_pos`, `hm_x` в `pvp.lua` | **Да**, адаптируется само |
| `hm_ys` в `pvp.lua:150–157` | **Нет** — жёсткие Y |
| Пороги Y в `tether.position_to_area_number` (`player_tether.lua:22–84`) | **Нет** |
| `chunks_by_floor` (`pvp.lua:4–27`) | **Нет** |
| `not_in_normal_area`, списки в `not_in_hm` | **Нет** |

Вывод: **как только мир перестанет быть ванильным, `pvp.lua` и `player_tether.lua`
нельзя переиспользовать целиком** — только как образцы и источники приёмов.
Механика круга у тебя всё равно своя, так что это терпимо, но лучше знать заранее,
чем обнаружить на середине.

**4.4. Сейвы и реконнект.** EW различает New Game и Continue и синхронизирует слот.
Со своими слотами нужно проверить, что реконнект и «Continue» ведут себя как ожидается.
Не тестировал.

**4.5. `request_no_api_restrictions` действует только на `init.lua`** (см. `docs/00` §3) —
если планируешь `io.*` для выгрузки позиций (например, под внешний голосовой клиент),
делать это придётся из `init.lua` или из EW-контекста, но не из скрипта сущности.

## 5. Практический порядок

Не смешивай три изменения в одном шаге, иначе не поймёшь, что сломалось.

1. **Пустой режим.** `mod.xml` с `is_game_mode="1"` и всеми `ui_newgame_*`, без своих
   `magic_numbers`. Убедиться: виден в меню, выбирается, EW видит одинаковый режим
   у обоих игроков (в логе нет `"different gamemode"`), кооп работает.
2. **Слоты.** Добавить `game_mode_supports_save_slots="1"`, проверить слоты и Continue.
3. **Генерация.** Только теперь трогать `magic_numbers` / `BIOME_MAP` — и сразу проверять,
   что EW не поломался **на ванильном мире**.
4. **Своя арена.** И лишь затем — компактный мир, с готовностью переписать таблицы
   из §4.3 своими.

## 6. Полезные находки по EW, всплывшие по пути

- `player_sync.lua:193–195`: `ctx.proxy_opt.friendly_fire` и
  `ModSettingGet("quant.ew.team")` — **у EW уже есть понятие команды** для «свой/чужой».
  Для командного БР смотреть туда, а не изобретать своё.
- `ctx.proxy_opt.world_num` — номер мира в прокси; синхронизируется и сверяется между
  игроками (расхождение останавливает синхронизацию мира).
- `player_fns.get_current_slot(player)` — слот сохранения, синхронизируется как `current_slot`.

## 7. Название и описание режима в меню: переводы надо вписывать руками

Это неочевидно и стоило отдельного раскопа, поэтому фиксирую.

**Проблема.** `ui_newgame_name="$gamemode_synergis"` при пустой панели в меню. Причина:
**игра не читает `translations.csv` мода автоматически.** Она знает только
`data/translations/common.csv`. Файл, лежащий в папке мода, никто не открывает.

**Следствие №1.** Оба официальных режима (`nightmare`, `daily_practice`) используют ключи
`$gamemode_*`, которые уже лежат в ванильном `common.csv` — и **ни один из них не имеет
своего `translations.csv`**. Это не совпадение: им нечего сливать, они переиспользуют ваниль.

**Следствие №2.** Неразрешённый ключ рендерится **пустотой**, а не сырым текстом
`$gamemode_synergis`. Поэтому по внешнему виду меню **нельзя отличить** «ключ не найден»
от «ключ найден, но значение пустое». Учитывай это при диагностике.

**Как правильно.** Свой CSV надо **вручную вклеить** в `common.csv`:
`ModTextFileGetContent("data/translations/common.csv")` → добавить свои строки →
`ModTextFileSetContent("data/translations/common.csv", ...)`.

Рабочий образец лежит рядом, в EW: `mods/quant.ew/init.lua:657–691` — функция
`register_localizations(translation_file, clear_count)`. Она:

1. читает ванильный `common.csv`;
2. читает свой файл;
3. разбивает его по `[^\n]+` и **выбрасывает первые `clear_count` строк**;
4. склеивает и записывает обратно.

Вызывается она в `OnModPreInit()` (строка 691) — то есть на самой ранней стадии загрузки
мода, до того как строится главное меню.

**Важные следствия для формата файла:**

- **Заголовок в своём CSV нужен**, потому что `clear_count = 1` съедает первую строку
  (в ванильном файле заголовок уже есть). Поэтому обрезанный заголовок вида `,en,ru,,`
  безвреден — он всё равно отбрасывается. Главное, чтобы он был.
- Ключ в CSV пишется **без** `$`, а в `mod.xml` — **с** `$`.
- Все эталонные файлы (`common.csv`, `common_dev.csv`, `quant.ew/translations.csv`)
  используют **LF**, а не CRLF. Разбиение идёт по `[^\n]+`, поэтому при CRLF в конце
  каждой строки останется `\r`. Скорее всего не сломает (ключ в первом поле), но лучше
  привести к LF, как в эталонах.

**Чего я НЕ подтвердил.** Прямого примера, где модовый ключ резолвится **именно в панели
выбора игрового режима**, нет: функция в EW написана явно для этой цели, но её собственные
ключи (`entangled_*`) в коде EW нигде не используются, так что доказательства
работоспособности нет. Если не заработает за 10 минут — ставь в `ui_newgame_*` обычный
текст и не трать вечер: это подпись в меню, а не механика.
