# 06 — Построчный разбор `pvp.lua` из EW (743 строки)

Файл: `mods/quant.ew/files/system/pvp/pvp.lua`

Это **самый ценный файл для тебя во всём EW**: в нём уже решены высадка, таймеры,
учёт смертей, победа, телепорт, награды и очистка Holy Mountain. Ниже — разбор по секциям
с номерами строк и вердиктом для каждой: **брать / адаптировать / выбросить** — с прицелом
на выбранный тобой дизайн B (классический сужающийся круг).

---

## 0. Сначала — внешний контракт: кто ещё дёргает `pvp`

Это важно понять до чтения, потому что `pvp` — не самостоятельная система, а модуль,
на который завязаны другие:

| Кто | Строки | Что использует |
| --- | --- | --- |
| `init.lua` | 154–156 | `if ctx.proxy_opt.pvp then ctx.load_system("pvp") end` — **загружается только в режиме PvP из прокси** |
| `init.lua` | 353–355 | `util.add_cross_call("ew_pvp", function() return ctx.proxy_opt.pvp end)` |
| `local_health.lua` | 19–22, 26–29 | при уроне пишет `pvp.last_damage = <peer_id> убийцы>` — вот как определяется убийца |
| `local_health.lua` | 373–377 | при смерти: `pvp.move_next_hm(true)` — **точка входа «игрок умер»** |
| `spectate.lua` | 26–27, 44–49 | читает `pvp.floor`, `pvp.players_by_floor[pvp.floor][peer_id]` — кого можно смотреть |
| `player_arrows.lua` | 25–26, 57–61 | то же, для стрелок над игроками |

**Вывод для БР.** `pvp.lua` — не «библиотека», а игровой режим, жёстко привязанный к
`ctx.proxy_opt.pvp`. Если ты включишь PvP в прокси и начнёшь писать поверх — будешь воевать
с его раундами. **Рекомендую не включать PvP-режим в прокси**, а свой модуль написать
по образцу `pvp.lua`, но независимо. Тогда режим в прокси — `LocalPermadeath`
(нужен только для perma-death), а смерти ты отслеживаешь сам (см. §25).

Заодно — ловушка, которую легко скопировать: `spectate.lua:47` и `player_arrows.lua:59`
читают `pvp.hm_y`, но в `pvp.lua` `hm_y` — **локальная** переменная (строка 144), в таблицу
`pvp` она никогда не попадает. То есть эти проверки всегда ложны. Не повторяй этот паттерн:
всё, что читается снаружи, должно быть полем таблицы.

## 1. `chunks_by_floor` — таблица координат биомов (строки 4–27)

```lua
local chunks_by_floor = {
    { { -3, 1, 3, 1 }, { 0, 0, 2, 0 } }, -- (Collapsed) Mines
    { { -6, 3, 3, 4 }, { -7, 3, -7, 3 } }, -- Coal Pits
    { { -5, 6, 4, 8 } }, -- Snowy Depths
    ...
}
```

Внутри — **прямоугольники в координатах чанков** `(x1, y1, x2, y2)`, по одному биому на запись.
22 биома, от Mines до The Tower. Позже их разворачивают в плоский список чанков
(строки 515–522) и берут случайный.

**Вердикт: БРАТЬ КАК ЕСТЬ.** Это готовая карта «где в мире что лежит», и она бесценна.
Учти: это не полная карта мира, а только «интересные» области, где EW селит игроков.

## 2. `names_by_floor` (строки 29–52)

Человекочитаемые названия тех же биомов в том же порядке. Нужны для сообщений
и для HUD («вы в Snowy Depths»).

**Вердикт: БРАТЬ.** Но осторожно: `pvp.lua` индексирует их как
`n = pvp.floor % #names_by_floor` (строка 462) с поправкой на 0 — кривовато, лучше
сделать нормальную функцию `biome_by_index(i)`.

## 3. Переопределение для Apotheosis (строки 54–119)

Если включён мод `Apotheosis`, таблицы подменяются на его биомы.

**Вердикт: ВЫБРОСИТЬ.** Это совместимость с конкретным большим модом. Но запомни **приём**:
условная подмена таблиц через `ModIsEnabled("...")` — так делается поддержка чужих модов.

## 4. `needs_ase` (строки 121–126)

```lua
local needs_ase = { "Wizards Den", "Magical Temple", "Ant Nest", "Temple of Sacrilegious Remains" }
```

Биомы, где игроку нужно снять «туман войны» (`REMOVE_FOG_OF_WAR`), иначе он играет вслепую.
Реализация — строки 466–495.

**Вердикт: АДАПТИРОВАТЬ.** Для БР это важнее, чем кажется. В режиме с зоной можно
использовать **туман войны как механику**: `GameGetFogOfWar(x, y)` / `GameSetFogOfWar(x, y, v)`
(`lua_api_documentation.txt`, строки 169–171) позволяют затемнять всё вне круга —
это дешёвый и очень читаемый визуал зоны, работающий на клиенте без сети.

## 5. `player_count`, `my_num`, `my_pw`, `pvp.floor`, `my_wins` (строки 128–136)

`my_pw` — **номер параллельного мира** (`+1` = первый восток, `-1` = первый запад).
Раскладывается так (строки 211–227):

```lua
my_pw = math.ceil((my_num + 1) / 2)
if my_num % 2 == 1 then my_pw = -my_pw end
...
hm_x = my_pw * BiomeMapGetSize() * 512
```

То есть игроков **намеренно раскидывают по параллельным мирам**, чтобы каждый играл
в своей копии Holy Mountain.

**Вердикт: ЭТО НАДО ПЕРЕОСМЫСЛИТЬ, И ЭТО КЛЮЧЕВОЕ РЕШЕНИЕ ДЛЯ ДИЗАЙНА B.**

Параллельные миры отстоят друг от друга на `BiomeMapGetSize() * 512` пикселей по X
(это десятки тысяч пикселей). Общий круг в таких координатах физически невозможен.
Варианты:

- **B1 (рекомендую): все в одном мире.** `my_pw = 0` для всех. Тогда круг работает
  в обычных мировых координатах. Минус: Holy Mountain у всех общий — надо решать, что с ним.
- **B2: свой круг в каждом параллельном мире.** Каждый мир — свой «матч», победители
  встречаются в финале в мире 0. Сложно и странно.
- **B3: круг посчитать на мир 0, а игроков в параллельных мирах считать «вне зоны»** —
  фактически запрет параллельных миров. Проще всего: телепортировать в мир 0 при высадке.

Разбор `GetParallelWorldPosition(world_x, world_y)` (документация, строка 87) и
`check_parallel_pos(x)` (используется в `player_tether.lua:345`) — твои инструменты здесь.

## 6. `player_died`, `pvp.last_damage`, `pvp.players_by_floor` (строки 138–148)

```lua
local player_died = {}          -- [floor] = { [peer_id] = true }
pvp.players_by_floor = {}       -- [floor] = { [peer_id] = true }
```

`alive = { [peer_id] = true }`, `died_this_phase = {}`.

## 8. `create_board()` — таблица победителей (строки 171–209)

Рисует физические сущности в Holy Mountain: сортирует `wins`, создаёт сущность на каждую
запись, ставит спрайт и текст.

Два ценных приёма:

```lua
nickname.add_label(ent, tostring(n), "data/fonts/font_pixel_white.xml", 0.75, 0.5, -12, -6)
EntityAddComponent2(ent, "SpriteComponent", {
    image_file = "mods/quant.ew/files/system/player/tmp/" .. p .. "_icon.png", alpha = 0.5 })
```

- `nickname.add_label(...)` — готовый способ нарисовать текст в мире.
- `mods/quant.ew/files/system/player/tmp/<peer_id>_icon.png` — **EW динамически генерирует
  иконку для каждого игрока** по его peer_id. Это твой способ нарисовать чужое лицо на
  HUD, на карте и на экране результатов.

**Вердикт: АДАПТИРОВАТЬ.** Экран результатов БР — это тот же код, только вместо
Holy Mountain — свой экран/зона.

## 9. `rpc.recv_player_num` / `rpc.get_player_num` — раздача номеров (строки 211–236)

Хост раздаёт игрокам порядковые номера, попутно назначая параллельный мир (см. §5),
и сохраняет всё в `GlobalsSetValue("ew_num"/"ew_pw"/"ew_player_count")`.

**Вердикт: АДАПТИРОВАТЬ.** Тебе нужен нормальный ростер: `peer_id → { team, index }`.
И учти слабое место этого кода — `player_count` считается **инкрементом при подключении**
и не уменьшается при выходе игрока. Для БР это фатально: «осталось 3 живых» при двух
отключившихся. Делай ростер от `ctx.players` и вычищай по `dc`/`leave`
(`net_handling.lua:105–138` — там `net_handling.proxy.dc` и `.leave`).

**Вердикт: АДАПТИРОВАТЬ** в «объявление победителя матча БР» + финальный экран.

## 11. `rpc.died`, `rpc.remove_floor`, `rpc.add_floor` (строки 262–296)

Механика «кто в каком раунде жив»: игрок добавляет себя в `players_by_floor[f]`,
при смерти — в `player_died[f]`, при уходе — удаляется.

Вишенка: `rpc.add_floor(f, ping, msg)` — если игрок впервые заходит и хост ещё не в HM,
он «пинает» остальных, чтобы те тоже отметились (строки 293–295). Это как раз решение
проблемы «поздний присоединившийся не попал в учёт».

**Вердикт: АДАПТИРОВАТЬ.** Для БР: `alive[peer_id] = true/false`, плюс обработка
опоздавших (в БР — либо не пускать, либо спавнить мертвым/спектатором).

## 12. `float()`, `set_camera_pos()`, `tp()` (строки 298–322) — **недооценённый золотой код**

```lua
local function float()
    local character_data = EntityGetFirstComponentIncludingDisabled(ctx.my_player.entity, "CharacterDataComponent")
    ComponentSetValue2(character_data, "mVelocity", 0, -40)
end

local function set_camera_pos(x, y)
    local cam = EntityGetFirstComponentIncludingDisabled(ctx.my_player.entity, "PlatformShooterPlayerComponent")
    ...
    ComponentSetValue2(cam, "mDesiredCameraPos", x, y)
end

local function tp(x, y)
    ctx.stop_cam = true
    set_camera_pos(x, y)
    EntitySetTransform(ctx.my_player.entity, x, y)
    async(function()
        wait(4)
        EntitySetTransform(ctx.my_player.entity, x, y)
        float()
    end)
end
```

Здесь три нетривиальные вещи, до которых сам бы дошёл не сразу:

1. **телепорт надо повторить через 4 кадра** — иначе движок «отпружинит» игрока назад;
2. **камеру надо вести принудительно** (`mDesiredCameraPos`), иначе будет рывок;
3. **`float()`** подбрасывает игрока вверх — чтобы не оказаться зажатым в материале;
4. `ctx.stop_cam` — флаг EW, чтобы его собственные системы не воевали с тобой за камеру.

**Вердикт: БРАТЬ КАК ЕСТЬ.** Это база высадки и телепортов. Вынеси в свой `util`.

## 14. `spawn_items(x, y)` — генератор магазина (строки 342–415) — **второй золотой код**

Это полноценный «ящик с лутом», собранный из ванильных генераторов:

```lua
dofile_once("data/scripts/items/generate_shop_item.lua")
...
SetRandomSeed(x + dx, y + dy)          -- ← детерминированный сид от КООРДИНАТ
local count = tonumber(GlobalsGetValue("TEMPLE_SHOP_ITEM_COUNT", "5"))
...
local ent = generate_shop_item(x + (i-1)*item_width + dx, 15360 + dy, true, nil, true)
...
LoadPixelScene("data/biome_impl/temple/shop_second_row.png", ..., x - 8, y - 22, "", true)
```

Приёмы, которые надо забрать:

- **`SetRandomSeed(x + dx, y + dy)`** — сид от позиции. Это ровно тот принцип
  «детерминированный лут по координатам», о котором речь в `docs/01`, но применённый
  к ванильным генераторам магазина. Так ты получаешь **одинаковый ассортимент у всех
  игроков без единого пакета**.
- Перед спавном код **убивает уже существующие платные жезлы и спеллы** (строки 360–371) —
  чтобы не было дублей при повторных вызовах.
- `LoadPixelScene(...)` ставит декорацию-подставку под предметы.
- `GlobalsGetValue("TEMPLE_SHOP_ITEM_COUNT", "5")` — читает ванильную константу вместо хардкода.

**Вердикт: БРАТЬ СЕРДЦЕМ.** Для БР это твой «сундук/ларек с лутом». Только не забудь:
`generate_shop_item` в EW перехвачен и синхронизируется (`gen_sync`), поэтому спавн
на хосте корректно уезжает клиентам.

## 15. `pvp.move_next_hm(died)` (строки 419–501) — переход между раундами

Что делает по шагам:

1. выключает `InventoryGuiComponent` (422–423) — чтобы игрок не лез в инвентарь в момент телепорта;
2. `hm_y = hm_ys[min(floor, #hm_ys)]`, `tp(hm_x - 677, hm_y)`;
3. если раундов больше, чем HM — выдаёт награду (строки 424–435):
   `heart_fullhp_temple.xml`, `spell_refresh.xml`, `perk_spawn_many(x, y)`,
   помечает перки «эфемерными» (`util.make_ephemerial`), затем `spawn_items(...)`;
4. если игрок умер (`died`) — `rpc.died(floor)` и кража золота у убийцы (436–457);
5. `pvp.floor = pvp.floor + 1`, `GlobalsSetValue("ew_floor", ...)` (458–461) —
   **состояние матча живёт в Globals и переживает сейв**;
6. логика тумана войны для `needs_ase` (466–495);
7. `async(wait(1))` и включение инвентаря обратно (496–499);
8. перерисовка таблицы (500).

**Вердикт: РАЗОБРАТЬ И ПЕРЕПИСАТЬ ПОД КРУГ.** Для дизайна B переход между раундами
заменяется на «смена фазы зоны». Но **все четыре подмеханизма остаются**:

- блокировка инвентаря на время перехода;
- **награда между фазами** (хп/спелл/перк) — в БР это спорно; скорее выдавай лут-кэш
  в центре новой зоны;
- фиксация смерти и определение убийцы;
- сохранение состояния матча через `GlobalsSetValue` (иначе рестарт/подключение
  всё потеряют).

## 16. `pvp.teleport_into_biome()` (строки 503–549) — **ВЫСАДКА, бери почти целиком**

```lua
SetRandomSeed(tonumber(string.sub(ctx.my_id, 8, 12), 16), tonumber(string.sub(ctx.my_id, 12), 16))
n = Random(1, #chunks)
local my_chunk = chunks[n]
local x = my_chunk[1] * 512 + 256
local y = my_chunk[2] * 512 + 256
tp(x, y)
LoadGameEffectEntityTo(ctx.my_player.entity, ".../pvp/safe_effect.xml")   -- неуязвимость
async(function()
    wait(8)
    LoadGameEffectEntityTo(ctx.my_player.entity, ".../pvp/tp.xml")        -- визуальный эффект
    float()
    wait(16)
    x, y = EntityGetTransform(ctx.my_player.entity)
    LoadPixelScene(".../pvp/tp.png", "", x - 6, y - 6, "", true, true)
    wait(16)
    local did_hit_down, _, _ = RaytracePlatforms(x, y, x, y + 2)
    if did_hit_down then                    -- ← упал в стену: повторить
        LoadGameEffectEntityTo(ctx.my_player.entity, ".../pvp/tp.xml")
        float()
        wait(16)
        x, y = EntityGetTransform(ctx.my_player.entity)
        LoadPixelScene(".../pvp/tp.png", "", x - 6, y - 6, "", true, true)
    end
end)
```

Что забрать:

- **координаты чанков → мировые: `x = cx * 512 + 256`** (центр чанка);
- **`safe_effect.xml`** — готовый эффект неуязвимости на время высадки;
- **проверка `RaytracePlatforms` вниз + повтор** — защита от спавна в стене;
- **`async/wait`** — Noita-корутины (`dofile_once("data/scripts/lib/coroutines.lua")`),
  без них тут не обойтись, потому что игрок «доезжает» физикой только через несколько кадров.

Что заменить: `SetRandomSeed` от **peer_id** даёт *разные* места каждому игроку — для
дизайна B тебе нужно наоборот: **сид матча + индекс игрока**, чтобы точки высадки были
равномерно раскиданы *по периметру будущего круга*, а не по всему миру.

## 18. `pvp.on_world_update_host()` (строки 577–613) — **каркас host-authoritative машины**

```lua
function pvp.on_world_update_host()
    if ctx.proxy_opt.timed then
        if tmr == nil then
            if hm_y ~= nil then tmr = 60 * ctx.proxy_opt.time_in; is_hm = true
            else tmr = 60 * ctx.proxy_opt.time_out; is_hm = false end
            rpc.update_timer(tmr)
        else
            tmr = tmr - 1
            if tmr == 0 then rpc.timer_ended(is_hm); tmr = nil
            elseif GameGetFrameNum() % 20 == 14 then rpc.update_timer(tmr) end   -- ← синк 3 раза/сек
            ...
```

Ключевые приёмы:

- **таймер синхронизируется не каждый кадр**, а раз в 20 кадров (`% 20 == 14`) — трафик в 20 раз меньше;
- хост **останавливает** таймер при выполнении условия (`n == player_count` или `n == 0`);
- вся логика под `on_world_update_host` — уже готовая развилка «только хост».

**Вердикт: БРАТЬ КАК КАРКАС.** Твоя машина фаз круга — та же форма:
`phase_timer`, `if tmr == 0 then advance_phase() end`, периодическая рассылка.

## 19. `pvp.on_world_update()` (строки 615–730) — главный цикл

Разбит на четыре смысловые части:

**19a. Инициализация (616–642).** Читает состояние из `GlobalsGetValue`
(`ew_player_count`, `ew_num`, `ew_pw`, `ew_floor`, `ew_wins`), и если номер не назначен —
либо назначает сам (хост), либо просит хоста (`rpc.get_player_num()`), затем сразу
`teleport_into_biome()`. Есть защита: клиент ждёт, пока хост появится в `ctx.players`.

**19b. Условие «я вышел за пределы области» (646–665).** Если игрок ушёл из Holy Mountain
по Y или по X дальше 8 чанков — либо возвращает в текущий HM (если живы игроки на
предыдущем этаже и включён `wait_on_players`), либо высаживает в новый биом.

**Вердикт: ЭТО ТВОЙ ПРОТОТИП ГРАНИЦЫ ЗОНЫ.** Замени «вышел из HM» на «вышел из круга»
(`dx*dx + dy*dy > r*r`), и получишь ту же логику: либо урон, либо телепорт назад, либо
принудительный переход фазы.

**19c. Условие победы (666–685).**

```lua
if player_count ~= 1 and GameGetFrameNum() % 60 == 32
   and #player_died[pvp.floor] == player_count - 1
   and not table.contains(player_died[pvp.floor], ctx.my_id) then
    pvp.move_next_hm(false); my_wins = my_wins + 1
    GlobalsSetValue("ew_wins", ...); rpc.win(my_wins)
end
```

Проверка раз в 60 кадров (не каждый кадр!) — и это правильно, потому что считает по таблице.

**Вердикт: АДАПТИРОВАТЬ.** Для БР: считаешь живых, при `<= 1` (или `<= 1` команда) —
`rpc.match_over(winner)`. Обязательно учитывай отключившихся.

**19d. Периодическая очистка Holy Mountain (686–729).** Убивает платные перки, жезлы,
спеллы и верстаки в HM каждые 121 кадр, **распределяя четыре разные проверки по разным
остаткам** (`% 121 == 27`, `== 47`, `== 67`, `== 87`).

**Вердикт: ЗАБРАТЬ ПРИЁМ.** Это готовый способ не убивать FPS: размазывай дорогие
проверки (урон по зоне, поиск игроков вне круга, спавн лута) по разным `% N == k`,
а не делай всё в одном кадре.

## Чего в `pvp.lua` НЕТ и что тебе придётся написать с нуля

1. **Круг как объект.** Нет ни центра, ни радиуса, ни фаз. Это твоя основная новая сущность:
   `zone = { cx, cy, r, phase, phase_start_frame, phase_end_frame }`.
2. **Интерполяция радиуса на клиентах.** Хост рассылает фазу (reliable, один раз),
   клиенты считают радиус сами от `GameFrameNum`/`ctx.host_frame_num`. Иначе трафик.
3. **Урон вне зоны.** Через `ctx.cap.health.inflict_damage(dmg)` — не через
   `DamageModelComponent` напрямую (см. `docs/02` §6 и `capabilities.md`).
4. **Визуал круга.** Пространственный образец: `quant.ew/files/system/player_tether/zone_entity.xml`
   + `set_tether_length()` — там уже параметризованный радиус частиц.
   Плюс дешёвый вариант: `GameSetFogOfWar` затемняет всё вне круга.
5. **Перенос центра круга.** `pvp.lua` просто телепортирует игроков; тебе нужно двигать
   геометрию и решать, что делать с теми, кто оказался вне при сдвиге.
6. **Одна точка входа в смерть.** `pvp.lua` получает её от `local_health` только при
   `ctx.proxy_opt.pvp`. Тебе нужен **свой** детектор: опрос
   `ctx.players[peer_id].status.is_alive` / `EntityGetIsAlive(player.entity)` на хосте.
7. **Политика Holy Mountain.** В БР Holy Mountain — дыра в балансе: там перки, хил, магазины
   и защита. Варианты: (а) вырезать содержимое (код очистки есть, 686–729);
   (б) вырезать телепорты и запереть (732–741); (в) считать HM частью зоны и позволять грабить.
   Решать тебе, но решить придётся.
8. **Один мир для всех.** См. §5 — ключевое решение, от которого зависит вся геометрия.

## Пересмотренные следствия для плана (см. `docs/04`)

Выбор дизайна B меняет приоритеты:

- **M8 (кастомная генерация) поднимается в приоритете.** На ванильном мире гигантского
  размера круг плохо работает: мир вертикальный, игроки копают, биомы вытянуты полосами.
  Компактная арена — это не «улучшение потом», а условие того, чтобы круг заработал красиво.
  Разумный порядок: сделать круг на ванильном мире (проверить механику), **затем** сразу M8.
- **Появляется новая задача, которой не было в исходном плане:** «все игроки в одном
  параллельном мире» + «политика Holy Mountain». Обе — до M6, иначе зона будет дырявой.
- **Урон и телепорты** (M6) теперь опираются на §19b и `player_tether` — кода для копирования больше.
- **Спектаторы** (`spectate.lua` из EW) уже работают, но завязаны на `ctx.proxy_opt.pvp`.
  Если ты не включаешь PvP в прокси — спектейт придётся включать своим кодом.
