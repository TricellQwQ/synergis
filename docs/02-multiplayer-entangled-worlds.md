# 02 — Мультиплеер: Quant's Entangled Worlds

## 0. Короткий вывод

**Свою сетевую часть писать не надо и практически невозможно.** В ванильном Lua-API нет ни
сокетов, ни сети. Единственный работающий путь в Noita — Entangled Worlds, и он даёт:
сетевой транспорт, RPC, синхронизацию игроков/предметов/врагов/пикселей мира и **уже готовый
позиционный голосовой чат** (см. `docs/03`).

Твоя задача — не «сделать мультиплеер», а **встроиться в EW** и написать поверх него логику БР.

Цена вопроса: ты навсегда зависишь от чужого мода, который ломается при обновлениях игры,
и чьи внутренности не обещают стабильности. Ниже — как минимизировать этот риск.

---

## 1. Архитектура EW из трёх частей

```
┌─────────────────────────────┐
│ noita_proxy.exe  (Rust)     │  отдельное приложение-лончер:
│  - GUI-настройки            │  хостит/подключается (Steam lobby или IP:port),
│  - Steam networking / UDP   │  ставит мод, ЗАПУСКАЕТ игру, синхронизирует мир,
│  - мир, карта, аудио        │  позиционный голосовой чат
└──────────┬──────────────────┘
           │ TCP/sockets (локально)
┌──────────┴──────────────────┐
│ noita.exe + ewext.dll       │  ewext.dll — Lua C-модуль (Rust),
│  ← грузится через           │  вставляет в Lua функции ewext.*
│    NoitaPatcher             │
└──────────┬──────────────────┘
           │ require("ewext")
┌──────────┴──────────────────┐
│ mods/quant.ew  (Lua)        │  init.lua + files/core + files/system + files/api
│  - ctx, net, RPC, системы   │  логика синхронизации
└─────────────────────────────┘
```

Как EW грузит нативный код (`mods/quant.ew/init.lua`, строки 1–13) — это **важно**, потому что
ровно так же ты сможешь подгрузить свой нативный модуль, если когда-нибудь понадобится:

```lua
dofile_once("mods/quant.ew/NoitaPatcher/load.lua")   -- подменяет do_mod_appends, чтобы
np = require("noitapatcher")                          -- прописать package.cpath/package.path
package.cpath = package.cpath .. ";./mods/quant.ew/?.dll"
package.path  = package.path  .. ";./mods/quant.ew/?.lua"
ewext = require("ewext")                              -- ← вот загрузка C-модуля
```

То есть: `noitapatcher.dll` → `noitapatcher` (API NoitaPatcher) → `ewext.dll` (API EW).
`NoitaPatcher` даёт в том числе `np.CrossCallAdd(name, fn)` — мост между Lua-контекстами.

## 2. Транспорт: что уходит в сеть

`mods/quant.ew/files/core/net.lua` — весь низкий уровень. Сообщение = строка, первый байт —
тип:

| Байт | Тип | Содержимое |
| --- | --- | --- |
| `1` | `mod` (RPC) | 8 байт peer_id (hex) + `bitser`-сериализованный `{key=..., value=...}` |
| `2` | `proxy` (строка) | `"<key> <value> [value2]"` — опции от прокси: `seed`, `peer_id`, `host_id`, `proxy_opt*`, `dc`, `leave` |
| `3` | `proxy` (бинарь) | `[key_byte] <binary>` — например, чанки мира (`proxy_bin_send`) |

Публичный API `net`:

```lua
net.new_rpc_namespace()              -- namespace с автоиндексом (для внутренних систем EW)
net.new_rpc_namespace_with_id(id)    -- ← используй ЭТО: префиксует индексы твоим id
net.send(key, value, reliable)
net.send_to_host(key, value, reliable)  -- ВНИМАНИЕ: реализовано как net.send, т.е. broadcast
                                        -- (в исходнике стоит "TODO actually only send to host")
net.proxy_send(key, value)              -- строковое сообщение в прокси
net.proxy_bin_send(key_byte, value)     -- бинарное сообщение в прокси
net.estimate_rpc_size(message)          -- прикинуть размер до отправки
```

**Ключевое ограничение: транспорт широковещательный.** Отдельного «клиент → только хост»
канала нет. Значит host-authoritative логику строишь так: рассылаешь всем, а выполняешь
только под `if ctx.is_host then ... end`.

## 3. Как встроиться: официальный стабильный API

`mods/quant.ew/files/api/ew_api.lua` — 13 строк, и это **единственное, что автор EW обещает
не менять** («Parts of EW api that are guaranteed to be stable»):

```lua
ew_api.new_rpc_namespace(id)   -- создать RPC-пространство имён
ew_api.rpc_player_data()       -- внутри rpc: данные игрока, который его вызвал
```

Подключение (это то, что ты напишешь в своём `init.lua`, на этапе загрузки мода):

```lua
if ModIsEnabled("quant.ew") then
    ModLuaFileAppend("mods/quant.ew/files/api/extra_modules.lua",
                     "mods/synergis/files/net/module.lua")
end
```

`extra_modules.lua` — это список файлов, которые EW исполняет **в своём контексте**.
Твой модуль должен вернуть таблицу; всё, что начинается с `on_`, EW вызовет как хук.
Полный список хуков — `mods/noita_entangled_worlds-master/docs/hooks.md`:

```
ctx.hook.on_world_initialized()
ctx.hook.on_new_entity(ents)
ctx.hook.on_world_update()               -- OnWorldPreUpdate
ctx.hook.on_world_update_post()
ctx.hook.on_world_update_client()        -- только клиенты
ctx.hook.on_world_update_host()          -- только хост
ctx.hook.on_new_player_seen(new_playerdata, player_count)
ctx.hook.on_local_player_spawn(my_player)
ctx.hook.on_client_spawned(peer_id, new_playerdata)
ctx.hook.on_should_send_updates()
ctx.hook.on_draw_debug_window(imgui)
ctx.hook.on_local_player_polymorphed(currently_polymorphed)
ctx.hook.on_client_polymorphed(peer_id, player_data)
ctx.hook.on_late_init()
```

То есть `on_world_update_host` уже даёт тебе готовое разделение «хост/клиент» — на нём и
строится БР-loop.

**Эталон: официальный пример-мод.** В репозитории EW есть `mods/noita_entangled_worlds-master/ew_api_example/` —
канонический шаблон внешнего мода: `init.lua` (3 строки), `module.lua`, `mod.xml`, `compatibility.xml`.
Его `module.lua` начинается так:

```lua
local ew_api = dofile_once("mods/quant.ew/files/api/ew_api.lua")

-- Needs a unique, but preferably short identifier.
local rpc = ew_api.new_rpc_namespace("api_example")
```

Ключевое: модуль **сам** загружает `ew_api.lua` через `dofile_once` — `ew_api` не глобальная переменная.
Путь `mods/quant.ew/...` при этом доступен, потому что твой модуль исполняется в контексте EW.

Поэтому тест RPC логично держать **внутри модуля** (§4.1) — так делает и сам пример: `init.lua` только
регистрирует append, а весь `rpc` объявлен в `module.lua`.

## 4. RPC: синтаксис и правила

Из `net.lua` (строки 57–94) и `ew_api_example/module.lua`:

```lua
local rpc = ew_api.new_rpc_namespace("synergis")   -- уникальный короткий id

rpc.opts_reliable()     -- доставить гарантированно и по порядку
rpc.opts_everywhere()   -- вызвать и у отправителя тоже
function rpc.spawn_zone(cx, cy, radius)            -- ← сразу после opts
    -- ctx.rpc_peer_id  = кто вызвал
    -- ctx.rpc_player_data = { name = ..., ... }
end
```

Правила, которые легко нарушить:

1. **`opts_*()` действуют на СЛЕДУЮЩЕЕ объявление функции** и потом сбрасываются.
2. `ctx.rpc_peer_id` / `ctx.rpc_player_data` не nil **только внутри вызова rpc**. Вне вызова —
   используй `ctx.players[peer_id]`.
3. `rpc.create_var(name, cb)` создаёт синхронизируемую переменную: `var.set(v)`, `var.values[peer_id]`,
   `var.prev_values[peer_id]`. Удобно для «состояния матча» и настроек хоста.
4. **Не занимай строковые ключи в `net_handling.mod`** — это общее пространство имён с внутренними
   системами EW (`inventory`, `perks`, `fire`, `welcome`, `join_notify`). Используй
   `new_rpc_namespace_with_id`, он нумерует ключи с префиксом твоего id.
5. Для «дешёвых» вещей (позиция, таймер) не ставь `opts_reliable()` — надёжная доставка дороже.
   И наоборот: спавн, смерть, конец матча — только reliable.

### 4.1. Как RPC устроен внутри (и почему это важно)

Всё держится на метатаблице `rpc_meta` из `net.lua:57-92`. Когда ты пишешь
`function rpc.hello(name) ... end`, происходит **не** то, что кажется:

1. твоё тело функции кладётся в общий список `net._rpc_inner.rpcs`;
2. функция получает **номер** — `local index = #rpc_inner.rpcs` (строка 60);
3. через `rawset` на место `rpc.hello` ставится **отправитель**: теперь `rpc.hello("x")` — это
   не вызов, а `net.send(index, { "x" }, reliable)` (строки 68-77);
4. **приёмник** регистрируется в `net_handling.mod[index]` и при получении вызывает то самое
   исходное тело, предварительно выставив `ctx.rpc_peer_id` и `ctx.rpc_player_data` (строки 78-90).

Отсюда — следствия, которые надо держать в голове:

- **Одно тело функции = и «что отправить», и «что делать при получении».** Отдельного обработчика
  писать не нужно; `ctx.rpc_peer_id` внутри вызова и есть «кто прислал».
- **Номер = порядок объявления.** Для namespace без id (обычный `net.new_rpc_namespace()`)
  это означает: **одинаковый код у обоих обязателен**. Если у друга другой набор или порядок
  `rpc`-функций, вызов «номер 7» выполнит у него другую функцию — и **без единой ошибки в логе**.
  Аналогия: рация с пронумерованным списком фраз; списки должны совпадать.
  Именно поэтому `ew_api.new_rpc_namespace(id)` (он же `net.new_rpc_namespace_with_id`) даёт
  **строковые** id вида `synergis0`, `synergis1` (строки 61-65) — они не зависят от порядка
  загрузки и не пересекутся с чужими.
- **RPC молча теряется**, если `player_fns.peer_get_player_data(peer_id)` вернул nil
  (`net.lua:81-86`) — например, игрок ещё не заспавнен. Ни ошибки, ни предупреждения не будет.
- **Сообщения-моды не принимаются, пока `ctx.ready == false`** (`net.lua:155`). А `ctx.ready = true`
  ставится в момент спавна локального игрока (`quant.ew/init.lua:431`) — то есть **до** хука
  `on_local_player_spawn` (строка 451). Практически: слать RPC имеет смысл начиная с этого хука.
- **Название функции не уходит в сеть** — только номер и аргументы. Поэтому переименование
  `rpc.hello` в `rpc.hi` безопасно, а вот **удаление или перестановка** — сдвигает номера у всех
  последующих (в namespace без id).

**Проверка в одиночку.** `rpc.opts_everywhere()` заставляет функцию выполниться и у отправителя,
поэтому объявленный `rpc` можно протестировать **без второго игрока**: хост-одиночка вызывает
`rpc.hello("me")`, и тело отрабатывает локально. Это проверяет весь путь, кроме собственно сети.

**Проверено на живом тесте вдвоём (12.10) — и первая попытка не сработала.** Оба игрока видели
в логе только **свой** вызов (`Hello from player <себя>`), а чужого `ctx.rpc_peer_id` не было ни
у кого. Причина — в порядке событий: `rpc.hello()` вызывался ровно один раз, в
`on_local_player_spawn`, а в этот момент либо партнёр ещё не подключился (друг заспавнился на 13
секунд раньше хоста), либо у принимающей стороны ещё **не было создано** `player_data` отправителя
— и EW выбросил сообщение молча (`net.lua:81-86`).

**Вывод, который надо применять ко всем сетевым сообщениям:** «отправить в момент своего спавна»
не работает. Слать надо тогда, когда партнёр уже виден в `ctx.players` (например, из ветки
`known == nil` в `refresh_roster`, §15.3), а для критичных вещей — с подтверждением: повторять
`hello`, пока не придёт ответный `ack`. Заодно в `hello` стоит положить версию мода и логировать
расхождение — тогда «у напарника другая сборка» видно сразу, а не проявляется десинком.

### 4.2. Рукопожатие с подтверждением: схема

Одноразовое сообщение в этом стеке не гарантирует ничего: получателя может ещё не быть в сессии,
а `player_data` отправителя на его стороне может быть не создана — и EW выбросит сообщение молча
(§4.1). Поэтому «отправил и забыл» для важных вещей не годится, а годится **сходящийся протокол**:
повторять, пока не придёт подтверждение.

**Протокол — два сообщения:**

```
A → hello(version)              «я здесь, моя версия X»
B → hello_ack(peer_id, ver)     «я тебя услышал, моя версия Y»
```

Правила, которые делают его завершаемым:

1. `hello` шлётся **повторно** (раз в ~30–60 кадров), пока от этого пира не пришёл `ack`.
2. Получив `hello` от пира P, отвечаем `hello_ack(P, …)` **только если сами ещё не отвечали P** —
   иначе двое будут отвечать друг другу бесконечно.
3. Получив `hello_ack(P, …)`, помечаем P подтверждённым: `hello` ему больше не шлём и сравниваем
   версии (кто прислал — подскажет `ctx.rpc_peer_id`).
4. Рукопожатие завершено, когда подтверждены **все** пиры из `ctx.players`, а не когда «я отправил».
5. Предохранитель: если за N секунд `ack` не пришёл — один раз написать `WARN` и прекратить
   повторы, чтобы не долбить сеть.

**Состояние** — на уровне модуля, рядом с `roster`:

```lua
local hs = {
    sent_frame = 0,    -- когда в последний раз слали hello
    acked      = {},   -- peer_id -> true: от кого уже получили ack
    ack_sent   = {},   -- peer_id -> true: кому мы уже отвечали
    done       = false,-- все пиры подтверждены
    tries      = 0,    -- предохранитель от бесконечных повторов
}
```

**Где вызывать.** Триггер — не свой спавн, а появление пира: ветка `known == nil` в
`refresh_roster` (§15.3). Плюс `on_world_update` с шагом: если есть неподтверждённые пиры и с
прошлой попытки прошло достаточно кадров — слать `hello` снова.

**Что логировать:** сам `hello` и пришедший `ack` — обязательно с **чужим** `peer_id` и версией,
расхождение версий — отдельной заметной строкой, и один итог вида `handshake complete (2/2)`.
Тогда закрытие пункта «первый RPC доходит» видно в логе обеих машин одной строкой.

**Про `rpc.opts_reliable()`.** Для рукопожатия его стоит включить (гарантированная доставка и
порядок), но **сам по себе он от этого выпадения не спасает**: `reliable` — свойство транспорта, а
сообщение теряется на уровне приложения, ещё до вызова обработчика. Спасает именно повтор.

**Упрощение: отдельный `ack`, скорее всего, не нужен.** `hello` идемпотентен, и «я тебя услышал»
подразумевается самим фактом, что я отправил свой `hello`. Тогда протокол становится
**односообщенческим**: держим набор `heard[peer_id]` и повторяем `hello` (раз в ~30–60 кадров, с
предохранителем) тем, от кого ещё **не слышали**. Пришёл `hello` от P — помечаем `heard[P]`,
логируем и по этому пиру замолкаем. Обе стороны сходятся к «слышали друг друга», и отдельного
второго типа сообщения не требуется.

**Обязательная оговорка при таком упрощении:** игнорируй собственный `hello`. С `opts_everywhere()`
обработчик выполняется и у отправителя, поэтому `ctx.rpc_peer_id == ctx.my_id` — это ты сам, и если
пометить себя как «услышанного», рукопожатие засчитается ложно. То же правило понадобится и
двухсообщенческой схеме, если вернёшься к ней.

**И вывод на будущее, важный для M3+.** Тот же принцип применим ко всей сетевой логике БР:
одноразовые события («игрок выбыл», «зона сместилась») в таком стеке ненадёжны. Надёжнее
реплицировать **состояние** (кто жив, где центр и радиус зоны) и периодически его повторять, а
события использовать лишь как ускоритель реакции. Иначе один потерянный пакет — и у игроков разная
картина матча.

### 4.3. Метки времени: точный кадр для событий, общий — для остального

Единственные общие часы в сессии — **кадр хоста** (см. §11.1 про `host_frame_num`). Отсюда простое
разделение:

| что логируем | что подставляем |
| --- | --- |
| кадр, посчитанный **хостом**, или кадр из payload события | `frame=` — точный кадр хоста |
| всё остальное (строки на клиенте, бытовые события) | `frame~=` — `shared_frame()`, приблизительный |

**Правило: точную метку ставит хост.** Для событий, которые он решает (зона, выбывание, конец
матча), это его собственный `GameGetFrameNum()` в момент решения, и он уезжает в payload:

```lua
-- на хосте
rpc.shrink_zone(cx, cy, radius, GameGetFrameNum())
```

**Клиентское `shared_frame()` для точной метки не годится.** У клиента это кадр хоста, каким он был
на момент последнего полученного апдейта, — то есть уже с задержкой. Поэтому события, идущие
**от клиента** (выстрел, подбор предмета, «я здесь»), отправляются как **запросы без метки**, а
точное время ставит хост при обработке:

```lua
-- клиент: rpc.try_pickup(entity)
-- хост:   в обработчике сам берёт GameGetFrameNum() и решает
```

**Оговорка про масштаб.** `GameGetFrameNum()` — счётчик текущего забега (живёт в сейве и переживает
перезапуск), поэтому сравнивать кадры **между разными забегами** нельзя, только внутри одного. Для
сопоставления разных запусков — настенное время.

**Практический смысл.** Почти всё важное в БР решает хост, поэтому у ключевых событий точная метка
получается «бесплатно». А вход/выход/дисконнект достаточно помечать `frame~=` — они нужны, чтобы
понять порядок событий, а не поймать миллисекунду.

## 6. Настройки: proxy_opt ≠ mod setting

Это неочевидно и важно. Часть конфигурации приходит **от прокси**, а не из `settings.lua` мода.
Прокси отправляет их сообщениями `proxy_opt`, `proxy_opt_num`, `proxy_opt_bool`
(`noita-proxy/src/net/proxy_opt.rs`) и их принимает `net_handling.proxy.proxy_opt*`.

Что EW так получает (по использованиям в Lua): `pvp`, `pvp_kill_steal`, `chest_on_win`,
`timed`, `time_in`, `time_out`, `wait_on_players`, `wait_for_time`, `perma_death`,
`no_notplayer`, `dont_steal`, `debug`, `log_performance`.

**Плохая новость:** игровой режим в прокси — это **захардкоженный Rust-enum**
(`noita-proxy/src/lib.rs`, строка 72):

```rust
pub enum GameMode { SharedHealth, LocalHealth(LocalHealthMode) }
enum LocalHealthMode { Normal, Alternate, PermaDeath, PvP }
```

Он выбирается в GUI прокси и уезжает в Steam-lobby data. **Свой режим туда не добавить без
форка прокси.**

**Практический вывод для БР:**

- Все свои настройки держи в `settings.lua` мода и читай через `ModSettingGet("synergis.*")` —
  это работает без единой правки прокси.
- Режим бери из существующих: `LocalPermadeath` (идеально для БР: умер = выбыл) или `PvP`.
- Форк прокси нужен только если захочешь: свой пункт режима в лобби, свой сетевой канал,
  или глубокую интеграцию с голосом. Это отдельный проект на Rust, не начинай с него.

**Не путай это с игровым режимом Noita.** Здесь речь про модель здоровья в прокси.
Отдельный пункт в меню New Game со своими сейвами и своими `magic_numbers` — это
**другая, независимая вещь** (`is_game_mode="1"` в `mod.xml`), и она совместима с EW.
См. [`docs/08-game-mode.md`](08-game-mode.md).

## 8. Ловушки, на которые ты обязательно наткнёшься

1. **Локальный спавн предмета не синхронизируется.** Если ты сделал `EntityLoad("...wand...")`,
   его увидишь только ты. Варианты: (а) `ctx.cap.item_sync.globalize(eid, instantly, peer_id)`;
   (б) генерировать лут на **всех** клиентах через `ProceduralRandom(x, y)` — тогда спавнить
   вообще не надо синхронизировать.
2. **`SetRandomSeed`/`Random` глобальны для контекста.** Рандом «в цикле по игрокам» даст
   разное на разных машинах. Сидируй детерминированно или считай только на хосте.
3. **Внутренности EW не стабильны.** Стабилен только `ew_api.lua`. Значит: пинить версию EW,
   писать защитно (`if ctx.players[id] == nil then return end`), не полагаться на поля
   `player_data`, которых нет в `ew_api`.
4. **Нет античита и нет авторитетности.** Клиент сам сообщает свои попадания. Для игры
   с друзьями — нормально; для публичного лобби — нет.
5. **Все игроки должны иметь одинаковый набор модов и версий.** Один лишний мод = рассинхрон.
   Прокси это проверяет и ругается.
6. **`request_no_api_restrictions="1"` не совместим с Steam Workshop.** Если мод нужен
   в Workshop — придётся отказаться от `io`.
7. **EW ломается при обновлениях Noita.** У него своя версия совместимости (`compatibility.xml`,
   `NP_SKIP_MOD_CHECK`). После патча игры жди обновления EW, а не правь его сам.
8. **Unsafe mods обязательны.** В меню модов надо включить «unsafe mods», иначе EW не загрузится.
9. **Порядок загрузки.** Не полагайся на то, что EW уже инициализирован в момент твоего
   `init.lua`. Всё, что требует EW, делай в хуках, а не на этапе загрузки файла.

## 9. Как тестировать мультиплеер в одиночку

Практические находки из репозитория EW:

- Прокси сам умеет запускать игру, и ему можно указать команду запуска:
  `noita_proxy --launch-cmd "noita.exe -gamemode 0"` (см. `Justfile`, цель `run2`).
- Переменные окружения: `NP_NOITA_ADDR` (адрес, куда прокси подключается к игре),
  `NP_APPID` (подменить app id, чтобы не мешать Steam), `NP_SKIP_MOD_CHECK=1`.
- Хостинг/подключение из CLI: `noita_proxy --host 5123` (или `--host steam`),
  `noita_proxy --lobby <code/ip:port>`.
- Для двух клиентов на одной машине нужно два экземпляра игры + два прокси с разными портами.
  Это неудобно, но выполнимо; альтернатива — вторая машина или виртуалка.

## 10. Чек-лист приёмки M2: что именно тестировать

«Оба загрузились в одном мире» — это только половина. Проверять надо по нарастающей, и каждая
ступень отвечает на свой вопрос.

### Ступень 0. Базовая линия — БЕЗ своего мода

Включить только `quant.ew`, свой мод выключить. Запустить лобби, подключиться, начать забег.
Убедиться, что кооп работает вообще: игроки видят друг друга, мир совпадает (копнуть в одном
месте — результат одинаковый), в логе нет сообщений о рассинхроне.

**Зачем это первым.** Если не работает здесь, проблема в EW, в версии игры или в сети, а не
в твоём коде. Без этой ступени любая ошибка будет выглядеть как «мой мод всё сломал».

### Ступень 1. Свой мод рядом с EW

| # | Что проверяем | Как понять, что прошло |
| --- | --- | --- |
| 1 | Мод грузится на **обеих** машинах | `logs/init.log` есть на обеих, шапка на месте |
| 2 | Набор модов одинаков | строка `Active mods - ...` в шапках **идентична** |
| 3 | Сид одинаков | `StatsGetValue("world_seed")` совпадает у обоих |
| 4 | Режим одинаков | в игре нет `is on a different gamemode number then you` |
| 5 | Игроки видят друг друга | визуально, плюс нет ошибок EW |

Пункт 2 — самый быстрый способ поймать классическую проблему: у одного друга не тот мод или
не та версия. Шапка твоего логгера печатает этот список, так что достаточно сравнить два файла.

### Ступень 2. Свой код в сетевом контексте

| # | Что проверяем | Как понять, что прошло |
| --- | --- | --- |
| 6 | Модуль подхватился | он логирует при загрузке |
| 7 | Мод видит состав сессии | в логе два `peer_id`, известно, кто хост |
| 8 | RPC доходит | сообщение одного появляется в логе другого |
| 9 | `io` доступен в контексте EW | `print(tostring(io))` даёт `table: ...`, а не `nil` |
| 10 | Выход игрока виден | друг выходит — в логе видно смену состава |

Пункты 6–10 делаются один раз и становятся каркасом всей сетевой части. Пункт 9 решает, сможет
ли сетевой модуль писать собственный лог напрямую, — от этого зависит устройство логирования
для всей сетевой логики (см. `docs/00` §6.2).

**Важно про логи двух машин:** сопоставлять их по локальному `GameGetFrameNum()` **нельзя** —
он принадлежит забегу и у игроков разный. Пиши в лог кадр хоста (`ctx.host_frame_num`) или
настенное время.

### Чего на M2 проверять НЕ надо

Синхронизацию жезлов, врагов, предметов, пикселей мира, грибных сдвигов, полиморфа — это уже
делает EW, и проверять чужую работу смысла нет. Свой геймплей (высадка, лут, зона, победа) —
это M3–M7.

Если ступень 0 не работает — дальше идти бессмысленно, и проблема почти всегда в версии
игры/EW или в наборе модов.

## 11. Как смотреть на сетевой контекст

Отладчика нет: контекст EW можно изучать только **изнутри** — кодом, который в нём исполняется.

**Подключение своего модуля.** В `init.lua`, на уровне файла, **до** `OnModInit`:

```lua
if ModIsEnabled("quant.ew") then
    ModLuaFileAppend("mods/quant.ew/files/api/extra_modules.lua", "mods/synergis/files/net/module.lua")
end
```

EW в своём `OnModInit` (`load_extra_modules()`) обходит эти appends и вызывает
`ctx.dofile_and_add_hooks(file)` — то есть `dofile_once` плюс регистрация всех ключей `on_*`
как хуков. Модуль исполняется **один раз** и обязан **вернуть таблицу** (та же грабля, что
с `log.lua`).

**Три окна наблюдения:**

| Способ | Что даёт | Ограничение |
| --- | --- | --- |
| `print` | консоль дев-сборки, префикс `LUA:` | работает всегда, но нигде не сохраняется |
| свой файл через `io` | история, которую можно грепать | сначала проверить, есть ли `io` в этом контексте; экземпляр логгера будет **отдельный** → пиши в отдельный файл (`logs/ew.log`), см. `docs/00` §6.2 |
| окно imgui — `on_draw_debug_window(imgui)` | живой дамп прямо в игре | нужен внешний мод-провайдер `load_imgui`; **ни игра, ни ваниль, ни установленные моды его не дают** (проверено поиском в `luacheck_config.lua`, ванильных скриптах, обоих `.exe` и всех модах) |

Синтаксис окна (если провайдер появится) — как в `quant.ew/files/system/debug.lua`:
`imgui.Begin(заголовок)` → `imgui.Text/Checkbox/Button/CollapsingHeader/GetWindowWidth` →
`imgui.End()`.

**Техника: дамп таблиц.** `tostring(ctx)` даёт бесполезное `table: 0x...`, поэтому нужен обход
`pairs`. Начинай с `_G` — какие глобалы вообще есть в этом контексте (фильтруй по типу и сортируй
ключи, иначе утонешь). Дальше `ctx`, `net`, `util`, `player_fns`, `ew_api`, `ewext`.
Для вложенных — рекурсия на 1–2 уровня: `ctx.players` → `pairs` по пирам → поля `player_data`.
Готовый образец печати таблиц лежит в Noita Arena: `lib/inspect.lua`.

**Порядок первых шагов** (по нарастающей, каждый проверяется отдельно):

1. Модуль-пустышка: печатает «загрузился», `tostring(io)` и список ключей `ctx`.
2. `on_world_initialized`: `ctx.my_id`, `ctx.host_id`, `ctx.is_host`, число пиров.
3. `on_new_player_seen(player_data, player_count)`: имя зашедшего.
4. Троттлинг-дамп состава в `on_world_update` (раз в 60 кадров): `peer_id`, имя, позиция.
5. RPC-hello.
6. Позже — окно imgui, если поставишь провайдера.

Из сетевого контекста **не логируй каждый кадр** — это дороже, чем в `init.lua`, потому что
рядом идёт сетевой обмен.

### 11.1. Проверено на практике

- **`io` в контексте EW доступен**: `print("io " .. tostring(io))` даёт `table: 0x...`. Значит
  сетевой модуль пишет свой лог **напрямую**, без мостов. Файл — **отдельный** (`logs/ew.log`):
  экземпляр логгера на каждый контекст свой.
- **`ctx.players` пуст в `on_world_initialized`** и заполняется только при спавне локального игрока
  (`quant.ew/init.lua:413`). Первый хук, где видно себя и состав, — **`on_local_player_spawn(my_player)`**
  (`quant.ew/init.lua:435`, вызывается уже после регистрации). Наблюдение с хоста-одиночки: `Players - 0`.
- **Префикс `print` зависит от сборки игры.** В dev-сборке строки из хуков идут как
  `LUA( mods/quant.ew/init.lua ): <текст>` — атрибуция ставится по месту **вызова**, а не по месту,
  где лежит код, поэтому в консоли ищи **по тексту сообщения**, а не по имени мода. В **обычной**
  сборке те же строки идут просто `LUA: <текст>`. Загрузка самого модуля в обоих случаях даёт
  `LUA: <текст>`.
- Для сопоставления логов с двух машин пиши в файл **`ctx.host_frame_num`**, а не локальный кадр.
- **`peer_id` — строка**, а не число (`"011000013a78d89d"`). `string.format("%d", peer_id)` роняет
  вызов (`bad argument #2 to 'format'`), и функция обрывается на этом месте — у нас из-за этого
  логгер не дописал строку, а в чат полетела ошибка. Нужен `%s`. Проверено.
- **`ctx.players` распаковывается только вручную**: `for peer_id, p in pairs(ctx.players) do` →
  `p.name` (ник), `p.entity` (id сущности). `print(ctx.players)` даёт `table: 0x...`, потому что
  у таблицы нет `__tostring`.
- **Имя папки мода критично.** Пути внутри мода хардкодятся как `mods/synergis/...` (аналога
  `ModGetPath` в Noita API нет — сверено по `tools_modding/luacheck_config.lua`). Если папка
  называется `synergis-main` (так распаковывается ZIP с GitHub), первый же `dofile_once` в
  `init.lua` падает, и в чат приходит
  `There were errors when initializing following mods: synergis-main`. Поэтому: папка ровно
  `synergis` + существующая папка `logs/` (она в `.gitignore`, в ZIP её нет — лечится `logs/.gitkeep`).
- **Для мультиплеера запускать только обычную сборку** (`noita.exe`) — см. §13.
- **`ctx.host_frame_num` ненулевой только у клиента.** EW кладёт в исходящие сообщения
  `GameGetFrameNum()` **только на хосте** (`player_fns.lua:328-331`), а сохраняет присланное
  значение **только принимающая сторона** (`player_fns.lua:275-276`). Хост своё же значение себе
  не присваивает, поэтому у него `ctx.host_frame_num` навсегда `0` (начальное значение —
  `ctx.lua:28`). Проверено на живом тесте: у хоста `frame=0` в каждой строке. Одно общее время на
  обеих машинах даёт помощник:

  ```lua
  local function shared_frame()
      if ctx.is_host then return GameGetFrameNum() end
      return ctx.host_frame_num
  end
  ```

  У клиента значение появится не сразу, а после того, как хост начнёт слать апдейты, — поэтому
  в самых первых строках (сразу после подключения) там тоже может быть `0`.

## 12. Если сеть блокирует Steam (актуально для РФ)

**Симптом.** Лобби создаётся и видно игроков, но данные не ходят: в чат бесконечно летит
`failed to send position` / `failed to send cursor`, а в логе — таймауты соединений.

**Причина.** Steam-нетворкинг работает **по UDP**, а большинство «стратегий обхода» умеют только
TCP (прокси на уровне приложения). Матчмейкинг при этом жив — он идёт через обычный API, — а
P2P-сессии таймаутятся. Это наблюдалось вживую на Noita Arena: `Session failed ...: 5003`
(`5003` = таймаут) для **всех** игроков лобби и ни одной строки `Session request from`, то есть
трафик не проходил ни туда, ни обратно.

**Что делать:**

- нужен режим обхода, который **пропускает UDP** (TUN/полный VPN), либо **исключить Steam**
  из обхода, а не заворачивать его в TCP-прокси;
- **обходной путь для EW: вообще не использовать Steam.** Прокси умеет работать по IP:

  ```
  noita_proxy --host 5123          # хостить по IP
  noita_proxy --lobby <ip:порт>    # подключиться по IP
  ```

- прямой IP требует доступности хоста извне, поэтому проще поднять **виртуальную локальную
  сеть** (Radmin VPN, ZeroTier, Hamachi): оба игрока оказываются в «локалке», порт-форвардинг
  не нужен, Steam в передаче данных не участвует;
- **где смотреть:** `ew_log.txt` в корне Noita — там подключения, порт и состояние сети.
  У Арены аналог — `noita_online_logs\noita-online.log`, там же видно `Session accepted: true`,
  когда связь появилась.

Порядок проверки при проблемах со связью: сначала исключить свой брандмауэр и антивирус, потом
VPN/обход, потом пробовать IP-режим через виртуальную локальную сеть.

## 13. Dev-сборка против обычной: главная ловушка M2

**Симптом.** При запуске `noita_dev.exe` с прокси и EW: два диалога `ASSERT FAILED!`
(`procedural_utils\biome.cpp`, строка 148, `seed <= (double)(INT_MAX-2) failed`), а в `logger.txt` —
`Couldn't get world info from NoitaPatcher`, `No entity sync module loaded`,
`Requested function does not exist` (`gun_actions.lua:8859`, `biome_modifiers.lua:1089`).

**Причина — не твой код.** NoitaPatcher (идёт в комплекте EW, `mods/quant.ew/NoitaPatcher/`) ищет
функции игры **по сигнатурам байтов**. У `noita_dev.exe` другой бинарник, поэтому часть поисков не
находит цель (`Couldn't find game mode items`, `Couldn't find duplicate pixel scene check`), и
цепочка рушится:

```
np.GetWorldInfo() → nil
  → nsew/world_ffi.lua:11  error("Couldn't get world info from NoitaPatcher.")
    → ctx.load_system("ewext_init")   (quant.ew/init.lua:64) не загружается
      → синхронизация сущностей не регистрируется
        → "No entity sync module loaded"   (ошибка из нативной части)
```

Подтверждение: строка `Requested function does not exist` встречается **только в `noitapatcher.dll`**
(в `noita.exe` и `noita_dev.exe` — 0 вхождений). То есть это NoitaPatcher не знает ванильную
`HasFlagPersistent`, которую вызывает ванильный `gun_actions.lua:8859`.

**Проверено:** в обычной сборке (`noita.exe`) через прокси мир генерируется, `ewext_init` грузится,
ошибок нет — `logger.txt` чистый, хуки и `ctx.players` работают. Диалоги `ASSERT` — тоже особенность
dev-сборки: в релизной он просто не скомпилирован.

**Сид и ассерты.** Прокси хранит сид как `u64` (`noita-proxy/src/net.rs:75`) и генерирует его через
`rand::random()` (`lib.rs:1579`), а `net_handling.proxy.seed` (`quant.ew/files/core/net_handling.lua:9-18`)
передаёт значение в `SetWorldSeed` **без обрезки**. Такой сид (~1.1e19) всегда больше `INT_MAX-2` —
отсюда диалог в dev-сборке. В релизной значение тихо приводится к допустимому
(`StatsGetValue("world_seed")` показывает нормальное число, у нас — `1713894839`).

**Настройки прокси** — всё в одном файле `%APPDATA%\quant\entangledworlds\config\proxy.ron` (формат RON):

- `paths.noita_exe` — какой exe запускать; по умолчанию `noita.exe`, это правильно;
- `game_settings.use_constant_seed` + `game_settings.seed` — фиксированный сид. Для
  воспроизводимых тестов удобно `use_constant_seed:true` и маленький `seed` (например `12345`):
  и ассертов нет, и мир одинаковый между запусками.

**Цена обычной сборки:** нет окна консоли. Отладка идёт через `logger.txt` в корне Noita (Lua-вывод
движка) и свой `logs/ew.log` из сетевого контекста; оба файла переживают перезапуск.

## 15. Вход, выход и дисконнект игроков

### 15.1. Что EW делает сам

| событие | обработчик | что происходит |
| --- | --- | --- |
| вход | `net_handling.mod.welcome` (`net_handling.lua:250`) | `ctx.events.new_player_just_connected = true`, затем `ctx.hook.on_should_send_updates()` |
| первый раз видим игрока | `player_fns.lua:588-598` | `ctx.events.new_player_seen = true` → `ctx.hook.on_new_player_seen(new_playerdata, count)` |
| спавн клиента | `player_fns.lua:602` | `ctx.hook.on_client_spawned(peer_id, new_playerdata)` |
| **дисконнект** | `net_handling.proxy.dc(_, peer_id)` (`net_handling.lua:105`) | игрок **остаётся** в `ctx.players`, `p.dc = true`, спрайт → `_dc.xml`, снимаются теги `ew_client` и `ew_peer` |
| **выход** | `net_handling.proxy.leave(_, peer_id)` (`net_handling.lua:129`) | `GamePrint("Player X left")`, **`EntityKill(player.entity)`**, **`ctx.players[peer_id] = nil`** |

**Хука выхода нет** — ни в `docs/hooks.md`, ни в `ctx.events` (там только события входа:
`new_player_just_connected`, `new_player_just_spawned`, `new_player_seen`, `inventory_maybe_just_changed`).

**Почему выход «не логируется».** `proxy.leave` удаляет запись из `ctx.players` в том же вызове, что и
убивает сущность. К моменту любого твоего обхода таблицы игрока там уже нет — список просто становится
короче, без события.

### 15.2. Почему смерть не заменяет отслеживание выхода

Соблазн логичный: раз `proxy.leave` убивает сущность, можно считать выход смертью и не городить отдельную
логику. Но есть три причины так не делать.

1. **EW сам смерти не детектит.** В его собственном PvP смерть **самообъявляется**: умирающий клиент
   вызывает `rpc.died(pvp.floor)` (`pvp.lua:437`), а раунд заканчивается по
   `#player_died[floor] == player_count - 1` (`pvp.lua:677`). Центральной детекции нет.
2. **`on_player_died` не использует ни одна система EW.** Движковый `OnPlayerDied` просто
   пробрасывается в `ctx.hook.on_player_died(player_entity)` (`quant.ew/init.lua:725-728`), а
   единственное упоминание в самом EW (`local_health.lua:34`) — закомментировано. То есть прецедента
   «срабатывает на удалённых игроков» и «срабатывает от `EntityKill`» нет: это допущение, которое надо
   проверять (см. §15.5).
3. **Атрибуция теряется.** Порядок в `proxy.leave`: сначала `EntityKill`, **сразу за ним**
   `ctx.players[peer_id] = nil`. Даже если смерть-событие придёт, к этому моменту записи в ростере уже
   нет — значит, некому приписать смерть: ни объявить в чат, ни посчитать выживших, ни определить
   победителя.

И отдельно: **`dc` — это вообще не смерть.** При мягком дисконнекте игрок жив, тело стоит в мире,
`ctx.players` не меняется. Смерти не будет никогда. Для королевской битвы это худший случай: тело в
мире, игрок числится живым, условие «остался последний» не наступает — матч висит.

### 15.3. Что делать: кэш ростера

Отдельная система слежки не нужна — нужен **кэш ростера** `peer_id -> { name, entity }`. Он окупается
трижды: ловит выход, даёт атрибуцию смертей и даёт место для обработки `dc`. И он всё равно понадобится:
без маппинга `entity -> peer_id` не построить ни киллы, ни лут («чей жезл выпал»), ни таблицу итогов.

**Шаг 1.** Таблица на уровне модуля (рядом с `rpc`, до `local module`):

```lua
local roster = {}   -- peer_id -> { name = ..., entity = ..., dc = ... }
```

**Шаг 2.** Функция сверки — вызывать её из `on_world_update`:

```lua
local function refresh_roster()
    local seen = {}

    for peer_id, p in pairs(ctx.players) do
        seen[peer_id] = true
        local known = roster[peer_id]

        if known == nil then
            roster[peer_id] = { name = p.name, entity = p.entity, dc = p.dc }
            log.info("players", "joined: " .. tostring(p.name) .. " [" .. peer_id .. "]")
        else
            known.name = p.name          -- ник мог измениться
            known.entity = p.entity
            if p.dc and not known.dc then
                known.dc = true
                log.info("players", "disconnected: " .. tostring(p.name))
            end
        end
    end

    for peer_id, known in pairs(roster) do
        if not seen[peer_id] then
            log.info("players", "left: " .. tostring(known.name) .. " [" .. peer_id .. "]")
            roster[peer_id] = nil        -- имя взяли из кэша, т.к. в ctx.players его уже нет
        end
    end
end
```

**Шаг 3.** Подключить в хуках:

```lua
    on_local_player_spawn = function(my_player)
        refresh_roster()        -- заполнить кэш собой
        -- ...
    end,

    on_world_update = function()
        if GameGetFrameNum() % 30 == 0 then   -- не каждый кадр: событие не требует такой точности
            refresh_roster()
        end
    end,
```

Именно `on_world_update` (а не `on_world_update_host`), потому что состав нужен на обеих сторонах.

**Шаг 4 (необязательно) — точное имя в момент выхода.** Вариант из §15.3 даёт имя из кэша, то есть на
один опрос (до 30 кадров) позже. Если нужно поймать момент, обработчик EW можно обернуть: `dofile_once`
возвращает **тот же самый** объект, что и у EW, поэтому подмена реально влияет на диспетчер.

```lua
local net_handling = dofile_once("mods/quant.ew/files/core/net_handling.lua")
local orig_leave = net_handling.proxy.leave

net_handling.proxy.leave = function(_, peer_id)
    log.info("players", "left (точный момент): " .. tostring(peer_id))
    if roster[peer_id] ~= nil then
        roster[peer_id] = nil
    end
    return orig_leave(_, peer_id)
end
```

**Внимание на сигнатуру.** Диспетчер вызывает обработчики как `fn(peer_id_отправителя, value, value2)`
(`net.lua:157-162`), поэтому **целевой** игрок приходит **вторым** аргументом — у EW он и назван `_`.
При обёртке это надо сохранить.

Минус этого варианта: это вмешательство во внутренности EW, и при обновлении мода ключ
`proxy.leave` может переименоваться. Вариант с кэшем устойчивее, вариант с обёрткой — точнее.

### 15.4. Политика для БР (решение за тобой)

- **`leave`** → игрок выбыл. Тут достаточно того, что ростер уменьшился: победу можно считать прямо по
  нему, отдельная ветка логики не нужна.
- **`dc`** → нужно решить явно, потому что автоматически он не рассосётся:
  - либо **сразу выбыл** (матч никогда не зависает) — но тогда надо и тело убрать из мира, иначе оно
    останется стоять;
  - либо **карантин** на N секунд на переподключение. Учитывая, что reconnect в EW, судя по коду, не
    предусмотрен, практичнее первый вариант.

### 15.5. Что проверить на тесте с другом

1. **Вход** — в логе `joined: <ник> [peer_id]` (у обоих).
2. **Выход** — друг выходит, у тебя `left: <ник>` с именем **из кэша**. Если строки нет — значит
   `proxy.leave` не пришёл или кэш не успел заполниться.
3. **Смерть в бою** — срабатывает ли `on_player_died` для **удалённого** игрока (это и есть проверка
   допущения из §15.2).
4. **Выход как смерть** — убивает ли `EntityKill` из `proxy.leave` событие `on_player_died`. Если да —
   часть логики можно упростить; если нет — кэш остаётся единственным путём.
5. **Дисконнект** — закрыть игру друга (или оборвать сеть), не выходя через меню: должен появиться
   `disconnected: <ник>`, а запись в `ctx.players` — **остаться** (`dc = true`).
6. **Спама нет** — при стабильной игре `refresh_roster` молчит (проверяется на одиночке).

### 15.6. Почему `on_client_spawned` — это не «вход игрока»

Кажется, что ветку «подключился» в `refresh_roster` можно убрать: вход ведь уже ловит хук. Но хук ловит
**не то событие**.

`on_client_spawned` вызывается из единственного места — `player_fns.spawn_player_for` (`player_fns.lua:602`),
а сама эта функция дёргается из **четырёх** разных мест:

| откуда | когда |
| --- | --- |
| `player_sync.lua:76` | реальный вход нового игрока |
| `player_fns.peer_get_player_data` (`player_fns.lua:521-526`) | **лениво, по требованию**: любой код, запросивший данные пира, которого ещё нет, создаёт ему сущность — и хук срабатывает |
| `player_fns.replace_player_entity` (`player_fns.lua:615`) | сущность игрока заменили |
| `player_fns.respawn_if_necessary` (`player_fns.lua:634`) | **респавн мёртвых**, вызывается регулярно — `init.lua:519`, каждые 16 кадров |

То есть `on_client_spawned` означает «у клиента появилась **сущность**», а не «**игрок** зашёл». За одну
сессию он сработает на игрока несколько раз: смерть → респавн → новая сущность (и новый `entity`).
Если строить кэш только на нём, получишь и дубли «joined» в логе, и протухший маппинг `entity → peer_id`.

**Принцип, который отсюда следует:**

> `peer_id` — это **состояние** (кто в сессии) → его даёт поллер по `ctx.players`.
> `entity` — это **событие** (появилось/умерло тело) → его дают хуки.

Поэтому кэш ключуется по `peer_id`, а `entity` в нём — просто обновляемое поле (`known.entity = p.entity`),
и смена сущности при респавне его не ломает.

**И то же самое про `on_new_player_seen`.** Он **не** значит «сейчас зашёл»: перед вызовом EW проверяет
сохранённый глобал `ew_seen_<peer_id>` (`player_fns.lua:590-600`), то есть условие — «этот peer_id
не встречался **в этом сейве**». Счётчик `ew_player_count` тоже персистентный. Для «кто зашёл сейчас»
этот хук не подходит.

**Практический вывод:** ветку «подключился» в `refresh_roster` оставляем — она и есть источник истины по
составу. А `on_client_spawned` используем для реакций на уровне тела (что-то привязать к новой сущности),
и, если нужна мгновенная реакция на вход, просто **вызываем `refresh_roster()` из хука** — тогда писатель
кэша по-прежнему один, но задержка в 30 кадров исчезает.

**Где что логировать, чтобы не было дублей:**

| место | что писать |
| --- | --- |
| `refresh_roster` | **все переходы состава**: `joined`, `left`, `disconnected`. Единственный источник этих строк |
| `on_local_player_spawn` | себя: `peer_id`, ник, `entity` + один снимок состава (`Players: ...`), затем `refresh_roster()` для заполнения кэша |
| `on_client_spawned` | **не** `joined`. Либо ничего, либо строка уровня тела (например `spawn`), плюс вызов `refresh_roster()` для мгновенной реакции |
| `on_player_died` | `died: <ник> [peer_id]` — через поиск `entity` в кэше |

Нюанс: **самый первый** `refresh_roster` покажет как `joined` всех, кто уже был в сессии до тебя — формально
это «уже здесь». Если такие строки не нужны, сделай засев «тихим»:

```lua
local function refresh_roster(quiet)
    -- ... if not quiet then log.info("players", "joined: ...") end
end

-- в on_local_player_spawn:
refresh_roster(true)                                    -- заполнить кэш молча
log.info("players", "snapshot: " .. player_list)        -- и один снимок списка
```

### 15.7. Отдельная ловушка для БР: EW респавнит мёртвых

`player_fns.respawn_if_necessary` (`player_fns.lua:624-641`) вызывается каждые 16 кадров
(`init.lua:519`) и для каждого игрока из `ctx.players`, чья сущность не жива, **создаёт новую**:

```lua
for peer_id, player_data in pairs(ctx.players) do
    if peer_id ~= ctx.my_player.peer_id and not EntityGetIsAlive(player_data.entity) then
        player_fns.spawn_player_for(peer_id, 0, 0, player_data)   -- вернулся
    end
end
```

В обычном EW это фича (после смерти игрок продолжает в следующем Holy Mountain, как в PvP-режиме EW:
`pvp.move_next_hm`). Но для королевской битвы это означает: **смерть ≠ выбывание**. Пока запись живёт в
`ctx.players`, EW будет возвращать игрока в мир.

Значит выбывание придётся делать **явно**: помечать игрока выбывшим у себя и убирать его из `ctx.players`
(тогда `respawn_if_necessary` его уже не увидит). Как именно — вопрос дизайна M3, но знать про это надо
заранее: иначе «убитые» будут возвращаться в зону.

### Наблюдения по событиям

**`disconnected` и `left` приходят почти подряд — это нормально.** Сначала срабатывает мягкий
дисконнект (`net_handling.lua:105`: игрок остаётся в `ctx.players` с `dc = true`), затем выход
(`net_handling.lua:129`: сущность убивается, запись удаляется). Ростер логирует оба события, и это
правильное поведение, а не двойной счёт.

**В строке `joined` может оказаться заглушка вместо ника.** EW создаёт `player_data` с именем
`[Peer <peer_id>]` (`player_fns.lua:377`), а настоящее имя приезжает отдельным RPC позже. Поэтому
первое событие входа логируется с заглушкой, а следующие строки — уже с настоящим ником: кэш
обновляет `known.name`. Если хочется красивого лога, не пиши `joined` до появления настоящего имени
или добавь отдельную строку про смену имени.

**Сущность игрока может заменяться.** В логе клиента было `Replaced player entity: 159 -> 472`
и затем `472 -> 544` — то есть `entity` у одного и того же `peer_id` меняется. Это ещё один довод,
почему кэш ключуется по `peer_id`, а `entity` — просто обновляемое поле (§15.6): идентифицировать
игрока по `entity` нельзя.
