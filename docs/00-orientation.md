# 00 — Ориентирование: как устроена модовая разработка в Noita

Это карта местности. Здесь нет «как сделать мод», здесь — **где лежит правда** и какие
грабли разложены на пути. Всё ниже проверено на твоей локальной установке.

Версия игры: `_version_hash.txt` = `9dbd52ced019a643169a2db02f46c77f8766c6e5`, ветка `master`.
Modding API версия: **12**.

## 2. Ванильные исходники: где их читать

Игра поставляет весь ванильный контент упакованным в `data/data.wak` (42 МБ). Пока он
упакован, ты не можешь прочитать ванильные `data/biome/*.xml`, `data/scripts/**/*.lua`,
`data/entities/**`. А это 90% ответов на вопрос «а как это сделано в оригинале».

**Ванильные исходники распакованы в профиле игры.** Туда их положила распаковка `data.wak`
(см. ниже) — полное дерево ванильных `data/`:

```
%USERPROFILE%\AppData\LocalLow\Nolla_Games_Noita\data\
```

На момент проверки там **14 745 файлов: 1077 `.lua` и 4325 `.xml`** — включая всё, что нужно:
`scripts\lib\utilities.lua`, `scripts\items\generate_shop_item.lua`,
`scripts\perks\perk_list.lua` (124 КБ), `biome\coalmine.xml`,
`entities\items\pickup\chest_random.xml`, `magic_numbers.xml`.

Это тот же ванильный код **от твоей версии игры**, поэтому вопрос «а как это сделано
в оригинале» решается грепом **здесь**, а не в зеркалах. Оговорка: после обновления игры
каталог может обновляться не сразу.

**Альтернатива — зеркало на GitHub**, если нужен поиск по коду в вебе или каталога нет:
[NathanSnail/noitadata](https://github.com/NathanSnail/noitadata). Может быть на другой
версии игры.

**Как получить это дерево.** По `tools_modding/READ_ME_FIRST.txt`: скопировать файлы из
`tools_modding/` в корень Noita и запустить `data_wak_unpack.bat`
(это `noita.exe -wizard_unpak`). По факту дерево оказалось именно в профиле игры, а не
в корне Noita — путь см. выше.

Дополнительно стоит положить в `tools_modding/` бинарник `luacheck.exe`
(ссылка в `lua_debugging.txt`) — тогда `luacheck_all.bat` начнёт проверять твой мод.

## 3. Анатомия мода

```
mods/synergis/
  mod.xml            манифест: имя, описание, флаги доступа к API
  init.lua           код в СОБСТВЕННОМ Lua-контексте мода
  settings.lua       настройки (УРЕЗАННЫЙ контекст: без io/os/dofile)
  files/             файлы мода, адресуются как mods/synergis/files/...
  data/              файлы с путями игры: ПЕРЕОПРЕДЕЛЯЮТ ванильные data/...
  data/generated/    автогенерируемое (sprite_uv_maps), руками не трогать
  compatibility.xml  version_built_with (необязательно)
  workshop.xml       для выгрузки в Workshop
  workshop_preview_image.png  16:9, для Workshop
```

Важные атрибуты `mod.xml` (полный список — на
[вики](https://noita.wiki.gg/wiki/Modding:_mod.xml)):

- `request_no_api_restrictions="1"` — даёт `os.*` и `io.*`.
  Цитата из официального шаблона: *«If a mod requires access to the full lua api e.g. os.* io.*
  it has to request access via 'request_no_api_restrictions="1"'. It is recommended that other
  options are explored first, as we may completely disable those APIs in the future.»*

  **Уточнение с вики, которое легко упустить:** флаг действует **только на контекст
  `init.lua`**. `LuaComponent` и прочие контексты остаются урезанными — то есть `io.*`
  в скрипте сущности не появится, сколько бы флагов ты ни ставил.

  Следствие: **такие моды не работают через Steam Workshop.** И ещё одно, которое легко
  не заметить: такие моды требуют включённого тумблера **unsafe mods** в меню модов — без него
  игра мод не загрузит, причём **молча** (ни ошибки, ни вывода).
- `is_game_mode="1"` — мод появляется в меню **New Game** как отдельный игровой режим
  и активируется, когда игрок его выбирает. Сопутствующие:
  `game_mode_supports_save_slots="1"` (несколько слотов сохранения),
  `ui_newgame_name`, `ui_newgame_description`,
  `ui_newgame_gfx_banner_bg` / `ui_newgame_gfx_banner_fg` (баннеры 64×36, путь обязательно
  полный, вида `mods/synergis/files/...`).

  **Для Synergis это рабочий вариант** — проверено, что он совместим с прокси EW.
  Что он даёт, чего стоит и какие таблицы в EW после этого сломаются —
  см. [`docs/08-game-mode.md`](08-game-mode.md).

## 4. Контексты Lua — главная ловушка для новичка

Noita исполняет Lua в **нескольких независимых Lua-стейтах**. Это не один общий `_G`.

1. **Контекст мода.** `init.lua` и `settings.lua` каждого мода. У каждого мода свой.
   Здесь доступны все игровые API-функции, но *твои собственные* функции не видны никому
   снаружи. `dofile_once` кэширует файл **внутри этого контекста**.
2. **Контекст игры.** `data/scripts/**/*.lua` и скрипты сущностей (`LuaComponent`,
   `script_item_picked_up` и т.п.). Тоже свой стейт. Функции из `data/scripts/lib/utilities.lua`
   живут здесь.
3. **Контекст EW** (см. `docs/02`) — отдельный стейт внутри мода `quant.ew`. Туда можно
   «дописать» свой модуль через `ModLuaFileAppend`.

Следствие: **`init.lua` не может просто так вызвать функцию из скрипта сущности и наоборот.**
Мосты между контекстами:

| Мост | Направление | Комментарий |
| --- | --- | --- |
| `ModLuaFileAppend(game_file, your_file)` | твой код → в контекст игры | Твой файл дописывается в конец ванильного. Классический приём: переопределить функцию, сохранив оригинал (`ew_orig_... = generate_shop_item`). |
| `ModTextFileSetContent(path, content)` | подменить файл игры целиком | Мощно и опасно. EW так вырезает часть сущностей. |
| `ModMagicNumbersFileAdd(path)` | подмешать magic_numbers | Так подключается своя `BIOME_MAP` и другие константы генерации. |
| `GlobalsSetValue/GlobalsGetValue` | общая шина, **сохраняется в сейв** | Так pvp.lua в EW передаёт `ew_floor`, `ew_player_count`. |
| `SessionNumbersSet/GetValue` | на текущую сессию | Не переживает сейв. |
| `GameAddFlagRun/GameHasFlagRun` | флаги забега | EW использует для идемпотентности спавна (`spwn_<fn>_<x>_<y>`). |
| `ModSettingGet("synergis.<id>")` | настройки | Самый простой способ донести конфиг до любого контекста. |
| `np.CrossCallAdd(name, fn)` / `CrossCall(name, ...)` | между контекстами | Это **NoitaPatcher**, не ваниль. Работает только если мод грузит `noitapatcher.dll` (так делает EW). Именно так EW зовёт свой сетевой код из скриптов сущностей. |

### 4.1. Полные имена и сигнатуры хуков

Эталонный список — комментарий самого движка в ванильном `data/scripts/init.lua` (строки 4–15):

| Хук | Что даёт |
| --- | --- |
| `OnPlayerSpawned( player_entity )` | игрок появился; **есть аргумент** — id сущности игрока |
| `OnPlayerDied( player_entity )` | игрок умер — основной сигнал для БР |
| `OnMagicNumbersAndWorldSeedInitialized()` | **мировой сид уже задан** — правильное место, чтобы его залогировать |
| `OnBiomeConfigLoaded()` | конфиги биомов загружены (пригодится на M8) |
| `OnWorldInitialized()` | мир инициализирован, но чанков вокруг игрока может ещё **не быть** |
| `OnWorldPreUpdate()` / `OnWorldPostUpdate()` | каждый кадр до и после обновления мира |
| `OnPausedChanged( is_paused, is_inventory_pause )` | пауза включилась или выключилась |
| `OnPausePreUpdate()` | кадр **на паузе** (мировые хуки в это время не вызываются) |
| `OnModSettingsChanged()` | игрок изменил настройки мода |

Плюс хуки, которые есть только у модов: `OnModPreInit()`, `OnModInit()`, `OnModPostInit()`.

**Почему `OnPlayerSpawned` приходит позже, чем `OnWorldInitialized`.** Так и задумано:
`OnWorldInitialized` срабатывает, когда мир создан, но чанки вокруг игрока ещё не загружены —
а игрока нельзя «заспавнить», пока для него нет места. На **загрузке сейва** между этими
событиями проходит заметное время, поэтому номер кадра в `OnPlayerSpawned` выглядит «большим».

### Что такое `GameGetFrameNum()` — проверено

Это **счётчик кадров текущего забега (сейва)**, а не времени и не кадров процесса:

- у нового забега стартует с нуля (`OnModPreInit` → 0, `OnWorldInitialized` → 1);
- **восстанавливается из сейва при загрузке** и продолжается с прежнего значения — даже после
  полного перезапуска игры;
- **не идёт во время загрузки и на паузе** — он считает кадры обновления мира, а не секунды.

Доказательство из практики: процесс запущен в `00:22:53`, `OnModPreInit` — в `00:22:58`
(то есть `GameGetRealWorldTimeSinceStarted() == 5.00` секунд), а кадр уже **1196**.
Через 6.9 секунды загрузки `OnWorldInitialized` показал **1197** — то есть за почти 7 секунд
реального времени счётчик прибавил ровно один кадр. Число 1196 ≈ накопленные кадры прошлой
сессии, сохранённые в сейве.

**Следствия для мультиплеера — это главное:**

1. **Локальный кадр — не общие часы.** У каждого игрока свой сейв и своя история, поэтому
   значения разные. Синхронизировать по нему фазы зоны или таймеры нельзя.
2. **Он замирает на паузе** (в том числе когда игрок открыл инвентарь). Любая логика «раз в
   N кадров» у этого игрока остановится.
3. **Для общего времени бери кадр хоста.** EW уже рассылает его: `ctx.host_frame_num`
   (`files/core/player_fns.lua:328–367` — хост отправляет свой `GameGetFrameNum()`,
   `:275–276` — клиенты его сохраняют). Плюс есть готовый кросс-вызов
   `ew_host_frame_num` (`files/core/util.lua:383–387`), который возвращает кадр хоста у клиента
   и свой у хоста — то есть им можно пользоваться и из игрового контекста.
4. Локальный счётчик используй **только для дельт и троттлинга** (`% 60 == 0`,
   «прошло 10 кадров с последнего урона»).

**Важно про паузу:** `OnWorldPreUpdate` не вызывается, пока игра на паузе (в том числе когда
открыт инвентарь). Если логика должна идти и на паузе — это `OnPausePreUpdate`.

## 5. Практические правила гигиены

- **Никогда не полагайся на порядок загрузки модов.** Проверяй `ModIsEnabled("quant.ew")`,
  `ModDoesFileExist(...)`.
- **Защищайся от nil.** `ComponentGetValue2` возвращает nil при неверном имени поля, и падение
  скрипта не всегда видно: в `logger.txt` попадает только движковое, а вывод Lua надо
  организовать самому (§6).
- **Линтер.** Гоняй `luacheck` с `luacheck_config.lua`: он знает список API и ловит
  `undefined variable` — в Lua без компилятора это половина всех ошибок. Прогоняй его
  **на каждый файл перед запуском игры**: синтаксическую ошибку он видит мгновенно, и это
  2 секунды против 2 минут перезапуска.
- **Ошибка на уровне файла в `init.lua` убивает весь мод.** Хуки, объявленные **ниже** упавшей
  строки, не определятся вовсе, и мод будет вести себя так, будто его нет — ни `print`,
  ни `GamePrint`, ни следа в логе. Причины бывают три: синтаксическая ошибка в подключаемом
  файле, рантайм-ошибка при его загрузке и — самое коварное — **отсутствие `return`** в конце
  подключаемого файла. `dofile_once` возвращает то, что вернул файл, поэтому без явного `return`
  ты получишь `nil`, на котором упадёт первое же обращение.
- **Как это ловить.** Проверяй, что вернул `dofile_once` (`type(x) == "table"`), но **не через
  ранний `return`** — он тоже оборвёт `init.lua` и убьёт хуки, то есть одна немая поломка
  сменится другой. Правильно — подставить заглушку и продолжать работать.
- **Если мод «молчит» и в консоли нет ни одной строки с его именем — он просто не включён.**
  Список включённых модов лежит в `save00\mod_config.xml` (`enabled="0"` / `"1"`), и таких файлов
  **два**: в профиле игры (`%USERPROFILE%\AppData\LocalLow\Nolla_Games_Noita\save00\`) и **в корне
  Noita**. Дев-сборка, судя по времени правки, пишет корневой, а обычная — профильный, так что мод
  надо включать **в той сборке, которую запускаешь**.
- **Ошибки Lua не попадают в `logger.txt`** (см. §6), поэтому «в логе чисто» ничего не доказывает.
  В консоли дев-сборки ищи по имени **своего мода** (`synergis`), а не по слову `error`.
- **Отладка.** Decoda + `noita_dev.exe -debug_lua` (`lua_debugging.txt`). `_G` в Watch-окне
  показывает весь стейт контекста. Помни, что контекстов несколько — смотри нужный.
- **Хот-релоада Lua в Noita нет.** Правка скриптов = перезапуск игры (или, для скриптов
  сущностей, иногда достаточно перезайти в забег). Планируй итерации соответственно:
  сначала алгоритм проверяй на «сухих» данных, потом в игре.
- **Не пиши в `data/generated/`** — это автогенерация.

### 5.1. Как пользоваться `luacheck`

Полный прогон (`luacheck_all.bat`) проверяет всю игру и все моды — долго и шумно. Для работы над
одним файлом, из корня Noita — одной строкой. **Перенос через `^` — это синтаксис `cmd.exe`,
в PowerShell он не работает** (там продолжение строки — обратный апостроф, и он капризный):

```powershell
tools_modding\luacheck.exe mods\synergis\files\lib\log.lua --config tools_modding\luacheck_config.lua --allow-defined --no-max-line-length -q --ignore 131 211 212 213 311 542 611 612 614 --globals print_error dofile_once async wait
```

Вместо файла можно указать каталог (`mods\synergis`) — тогда проверятся все `.lua` рекурсивно.

Если хочется многострочно, надёжнее массив и `&` (только не называй его `$args` — это
автоматическая переменная PowerShell):

```powershell
$lc = "tools_modding\luacheck.exe"
$p = @(
  "mods\synergis"
  "--config", "tools_modding\luacheck_config.lua"
  "--allow-defined", "--no-max-line-length", "-q"
  "--ignore", "131","211","212","213","311","542","611","612","614"
  "--globals", "print_error","dofile_once","async","wait"
)
& $lc @p
```

**Зачем флаги.** `--config` подключает `luacheck_config.lua`, где перечислены все функции API
Noita — без него каждый `EntityLoad`, `GamePrint` и прочее будет «неопределённым глобалом».
`--ignore` и `--globals` взяты из `luacheck_all.bat` и глушат предупреждения, нормальные для
модов (например, определение глобалов-хуков вроде `OnModInit`).

**Как читать вывод.** Формат `файл:строка:столбец: сообщение`. Коды возврата: `0` — чисто,
`1` — предупреждения, `2` — ошибки (включая синтаксис).

**Главное ограничение:** в каждом файле luacheck останавливается на **первой** синтаксической
ошибке — дальше файл просто не разбирается. Поэтому после каждой правки запускай снова: ошибок
может быть несколько, ты просто видишь их по одной.

**Чего он НЕ поймает:** всё, что синтаксически корректно. Примеры, уже встреченные в этом проекте:
`"/n"` вместо `"\n"` (валидная строка из двух символов), `os.name` (такого поля нет, условие
всегда ложно), `"текст" .. таблица` (ошибка типа на рантайме) и **отсутствие `return` в конце
модуля** — синтаксис и имена верны, а `dofile_once` вернёт `nil`. Линтер ловит **синтаксис
и имена**, а не логику и типы — тестировать в игре всё равно придётся.

## 6. Куда попадает вывод: `print`, `GamePrint`, логи

Самая частая потеря времени на старте — писать `print` и не находить его нигде.

| Способ | Куда идёт | Когда работает |
| --- | --- | --- |
| `print(...)` | в **стандартный вывод процесса**: видно в консоли `noita_dev.exe`, с префиксом `LUA:` | в любом контексте, в любой момент |
| `GamePrint(...)` | в **ленту сообщений на экране** | только когда есть запущенный мир |
| `GamePrintImportant(...)` | заметное сообщение вместо строчки в ленте | когда есть мир |
| `print_error(...)` | даёт **движок**: в ванильном Lua используется 14 раз и нигде не определён. Гипотеза — идёт в канал ошибок и **попадает в `logger.txt`**; не проверено | не проверено |
| свой файл через `io.open(path, "a")` | в **файл, который ты сам выбрал** | нужен `request_no_api_restrictions="1"` |

**`logger.txt` в корне Noita — это лог движка, а не Lua.** Туда попадают запуск, ошибки
загрузки файлов, проблемы Steam и статистики. Ни `print`, ни `GamePrint` там не появляются:
проверено поиском по всем `.txt` в корне игры и в `mods` — строк мода на диске нет вообще.

**Что видно в консоли дев-сборки** (`noita_dev.exe`; проверено на реальном запуске):

- каждая строка мода идёт как `LUA: <текст>`;
- движок сам трассирует вызовы хуков: перед `LUA: Synergis - OnModPreInit()` стоит строка
  `OnModPreInit`, то есть порядок хуков читается и без твоих логов;
- последовательность старта: `Mods init` → `Mod enabled: synergis` → `Calling init.lua` →
  `OnModPreInit` / `OnModInit` / `OnModPostInit` → `Mods init done` → …
  → `ProceduralTerrain::Init( data/scripts/biome_map.lua )` → `Generating world`.
  **Между хуками загрузки мода и генерацией мира ~15 шагов движка** — вот почему `GamePrint`
  в `OnModPreInit`/`OnModInit`/`OnModPostInit` показывать нечего, а `print` работает всегда;
- консоль — это стандартный вывод процесса, **своего файла у неё нет**. Чтобы сохранить:
  перенаправить stdout при запуске из cmd (`noita_dev.exe > log.txt 2>&1`) — не проверено,
  игра может сама создавать консоль и перенаправление не подхватится; либо писать свой
  файловый логгер.

**`F9` и уровни лога.** В обычной сборке эффекта не даёт (проверено). В **дев-сборке работает**
и переключает уровень вывода на экранную панель (проверено):

| Нажатие | Что показывается |
| --- | --- |
| 1 | только ошибки |
| 2 | ошибки + предупреждения |
| 3 | всё |
| 4 | панель скрывается |

`SHIFT+F9` очищает все уровни.

**Но это канал движка, а не Lua.** Содержимое панели совпадает с `logger.txt` по набору строк
(строгого доказательства, что это буквально один и тот же поток, нет; но главное проверено —
на уровне 3 своих `print` там не видно). Поэтому искать там вывод Lua бесполезно: в канал движка
он не попадает. Строки вида `Lua loading file: data/scripts/... - done`, которые видны на уровне 3, —
это сообщения **движка** о загрузке Lua-файлов, а не вывод Lua.

Дешёвая проверка, если сомневаешься: сделать `print` не на старте, а во время игры
(`OnWorldPreUpdate` с троттлингом) при уровне 3. Если строки не появились — вывод Lua в этот
поток не попадает вообще, и остаются только консоль дев-сборки и свой файл.

### 6.1. Чек-лист своей системы логирования

**Прецедентов нет.** `io.open` / `io.write` / `os.date` / `os.execute` не используются
**нигде**: ни в одном моде в `mods/`, ни в ванильных скриптах (0 совпадений). Готового образца
для копирования не существует — ты первый. Зато `debug.traceback` доступен (им пользуется EW),
а `pcall`/`xpcall` в ванильном Lua не используются вообще: ваниль ошибки не ловит, а тебе стоит.

**Где может жить логгер.** `io` доступен только в контексте `init.lua` и только с
`request_no_api_restrictions="1"` (флаг действует лишь на `init.lua` — см. §3). В `settings.lua`
нельзя. В скриптах сущностей (`LuaComponent`) тоже нельзя — если понадобится логировать оттуда,
нужен мост `np.CrossCallAdd` (так делает EW).

**Каталог.** Рабочий каталог игры — корень Noita, поэтому `mods/synergis/...` резолвится.
Но `io` **не создаёт каталоги**: `io.open("mods/synergis/logs/x.log", "a")` вернёт nil, если
папки `logs/` нет. Варианты: писать в корень мода (каталог уже есть), завести папку руками
с `.gitkeep`, или `os.execute("mkdir ...")` — лишний запуск `cmd.exe`.

**Один файл или несколько.** Один файл на сессию: обрезать в `OnModPreInit`, дописывать дальше.
Разделять по подсистемам (`match.log`, `zone.log`) **не стоит** — при отладке сети важна
хронология, а не группировка. Лучше один файл плюс тег подсистемы в каждой строке.

**Дескриптор.** Открывать-писать-закрывать на каждый вызов — просто и надёжно (данные на диске
сразу), но дорого при частых вызовах. Держать открытым — быстро, но при крахе потеряется хвост
без явного `f:flush()`, а на Windows файл будет занят всё время (не удалить, не переименовать).
Начинай с первого варианта.

**`io.open` при ошибке ввода-вывода возвращает `nil` и строку причины**, а не бросает
исключение — поэтому проверять результат надо всегда: `local f, err = io.open(path, "a")`.
Проверяй и сообщай о неудаче через `print`, а не через файл: иначе при неудаче открытия
ты не увидишь, почему её не видно.

Но есть важная разница: если **аргумент не строка** (`path == nil`, например из-за
потерянной переменной), это уже ошибка аргумента, и она **бросается**. До проверки
`if f == nil` дело не дойдёт — получишь «string expected, got nil».

**«Файл занят» — это не про твои контексты.** `fopen` под Windows обычно открывает файл
с разрешением совместного доступа, поэтому два своих дескриптора конфликта не дадут (но это
не гарантия — я не проверял, с каким share-режимом собран Lua-рантайм Noita). Настоящая проблема
другая: `fopen("a")` — это «встать в конец и записать», и если два контекста пишут в один файл,
между этими двумя действиями второй успевает записать → строка затирается. Ошибки не будет,
будет мусор в логе, который потом отлаживается как «баг логики». Ровно поэтому файлы по контекстам
разные. А «занят» реально может сказать **другой процесс**, открывший лог с эксклюзивным
доступом.

**Содержимое строки.** Метка времени, **номер кадра**, уровень, подсистема, сообщение.
`GameGetFrameNum()` и `GameGetRealWorldTimeSinceStarted()` доступны всегда; `os.date` — только
с флагом, поэтому проверяй `if os and os.date`. Кадр полезнее времени: по нему сопоставляются
логи разных машин.

**Не логировать каждый кадр.** Троттлинг как у EW: `if GameGetFrameNum() % 60 == 0 then`.
Порог уровня — из настроек мода.

**Два приёмника.** Файл — история, `print` — живой просмотр в консоли. Дублируй в оба: это и
решает задачу «все моды сливаются в один лог» — чужое в общей консоли, твоё в твоём файле.

**`.gitignore`.** Логи не коммитить (`*.log` или папку).

**Что логировать первым делом.** Не всё подряд, а то, без чего не отладить мультиплеер:
`peer_id`/`host_id`, вход и выход игроков, смены фаз матча, каждый RPC (кто, какой, размер),
рассинхроны (своё значение против значения пира). Свой логгер тут будет основным инструментом:
у EW своего логгера нет.

**Для сопоставления логов двух машин нужен общий отсчёт.** Локальный `GameGetFrameNum()`
для этого **не годится**: он принадлежит забегу и восстанавливается из сейва, а сейвы у игроков
разные — значения разойдутся (см. §4.1). Годится либо кадр хоста (`ctx.host_frame_num`, его
EW рассылает сам), либо настенное время (`os.date`). Поэтому сетевой модуль должен писать
в лог **кадр хоста**, а не локальный.

### 6.2. Где живёт логгер: отдельный файл, но по экземпляру на контекст

**Ответ на вопрос «в `init.lua` или отдельным файлом» — отдельным файлом.** Но с важной поправкой.

**Поправка: одного логгера «для всех файлов» быть не может.** Lua-таблицы не переходят между
контекстами. Код мода живёт минимум в трёх:

| Контекст | Что там | `io` доступен? |
| --- | --- | --- |
| `init.lua` твоего мода | хуки `OnMod*`, `OnWorld*` | **только с** `request_no_api_restrictions="1"` |
| контекст EW | твой модуль из `extra_modules.lua` — там будет вся сетевая логика БР | **скорее всего да**: `quant.ew` имеет флаг, а модули грузятся в его же контекст через `dofile_once`. Проверяется одной строкой: `print(tostring(io))` |
| контекст игры | скрипты сущностей, `data/scripts/*`, biome_map | **нет**, флаг на эти контексты не действует |

Поэтому «общий логгер» — это **один файл-модуль, загружаемый отдельно в каждом контексте**.
`dofile_once("mods/synergis/files/lib/log.lua")` внутри одного контекста вернёт **тот же самый**
экземпляр (кэш `dofile_once`), а в другом контексте — новый, со своим дескриптором файла.

**Практические следствия:**

1. Пиши `log.lua` как **фабрику**: модуль возвращает таблицу с методами
   (`log.info/warn/error(tag, msg)`, `log.set_level(n)`, `log.reset()`), а не полагается на
   глобалы. Так его можно поднять в любом контексте.
2. **Разные файлы для разных контекстов** (`logs/init.log`, `logs/ew.log`, `logs/game.log`).
   Если два контекста пишут в один файл разными дескрипторами, строки могут перемешаться:
   запись мелкая и в режиме append, но атомарность никто не гарантирует.
3. **Обрезать файл (режим `"w"`) должен только один контекст** — твой `init.lua`, в `OnModPreInit`.
   Остальные всегда открывают в `"a"`. Иначе порядок загрузки решит, кто сотрёт чужое.
4. **Порог уровня — из настроек мода** (`ModSettingGet("synergis.log_level")`): это игровой API,
   доступный во всех контекстах, поэтому все экземпляры получат одно значение. Документация
   советует кэшировать значение — читай при загрузке и обновляй раз в N кадров.
5. **Загружай `log.lua` в начале `init.lua`, на уровне файла**, до хуков — иначе `OnModPreInit`
   логировать нечего.
6. Не пытайся логировать из `settings.lua`: это отдельный урезанный контекст, ему недоступны
   ни `io`, ни загрузка чужих файлов.
7. Каталог под логи `io` не создаст — либо пиши в корень мода, либо заведи папку руками
   с `.gitkeep`, либо `os.execute("mkdir ...")`. И добавь логи в `.gitignore`.

### 6.3. API логгера и формат строки

**Две разные оси, которые легко слить в один «тег»:**

| Ось | Примеры | Где задаётся |
| --- | --- | --- |
| **Контекст** — в каком Lua-стейте исполняется код | `init`, `ew`, `game` | один раз, при создании логгера |
| **Подсистема** — какая часть логики пишет | `zone`, `match`, `net`, `loot`, `drop` | в каждом вызове |

Контекст фиксирован для экземпляра, поэтому его не надо передавать в каждый вызов — фабрика
`make_logger(context, path)` подставит его сама. Подсистему передавать надо: именно по ней потом
грепается лог. Список тегов держи **коротким и фиксированным**, иначе появятся `zone`, `Zone`
и `zone_shrink`, и grep перестанет работать.

**Функции уровней: делай и ядро, и обёртки.**

- Ядро — одно: `log.write(level, tag, msg)`. Вся логика (проверка порога, формат, открытие файла)
  только здесь.
- Обёртки — тонкие: `log.debug/info/warn/error(tag, msg)`, каждая в одну строку вызывает ядро
  с константой.

Почему не только `write(level, ...)`: уровень станет параметром-строкой, появится опечатка
(`log.write("eror", ...)`), и сообщение **молча исчезнет** — порог не пройден, ошибки нет.
Это худший вид бага в логгере: пропадает именно та информация, которую ты искал. Обёртки убирают
такую возможность полностью.

**Мелочи, которые стоит заложить сразу:**

- Уровни — **числа** (`LEVEL_DEBUG = 1` … `LEVEL_ERROR = 4`): сравнение дешёвое и сортируемое,
  а читаемые имена — сверху.
- **Проверка порога — первой строкой ядра**, до форматирования и открытия файла.
- Отдельный уровень `always`/`fatal`, игнорирующий порог: для строк «логгер поднят»
  и «не удалось открыть файл».
- Не называй что-либо `error` **глобально** — затенишь встроенную `error()`. `log.error`
  как поле таблицы безопасен.
- **Первая строка лога — шапка**: версия игры, версия мода, время старта, активный порог
  и путь к файлу. Без шапки лог через день нечитаем.
- **Номер кадра — с ведущими нулями** (`[00123]`): тогда обычная текстовая сортировка совпадает
  с сортировкой по кадрам, и слияние логов из двух писателей (§6.2) не требует скриптов.

Формат строки, закрывающий все эти задачи:

```
[00123] INFO  init/zone   : фаза 1, радиус 4096
```

Если в файл будет писать в основном одна подсистема, позже можно добавить `log.child("zone")` —
логгер с уже подставленным тегом. Но пока подсистем мало, проще передавать тег в каждом вызове.
