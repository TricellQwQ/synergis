# 09 — M3: каркас матча

Цель этапа (из [README](../README.md)): состояния **Lobby → Drop → Play → Results**, таймер фаз с
синхронизацией от хоста, HUD (таймер и число живых), условие конца матча.

Главное на старте: **почти всё это уже есть в EW в виде рабочего шаблона** — его собственный
PvP-режим делает то же самое. Не изобретаем, а разбираем и переносим.

---

## 1. Два принципа, на которых всё держится

**1. Состоянием владеет хост.** Клиент ничего не решает про фазы и время — он отображает то, что
пришло от хоста, и отправляет запросы. Это снимает целый класс рассинхронов.

**2. Состояние реплицируется, события — только ускоритель** ([docs/02](02-multiplayer-entangled-worlds.md), §4.2).
Одноразовое сообщение может потеряться; периодическая публикация состояния — нет. Поэтому таймер
ездит по сети **много раз**, а не одним сообщением «фаза началась».

## 3. Разбор таймера EW — это наш шаблон

Сокращённо, с сохранением структуры:

```lua
local gui
if ctx.proxy_opt.timed then
    gui = GuiCreate()                     -- один раз, на уровне файла
end

local time = 0                            -- ОТОБРАЖАЕМОЕ время (у всех)

rpc.opts_everywhere()                     -- чтобы хост тоже обновил своё `time`
rpc.opts_reliable()
function rpc.update_timer(t)
    time = t                              -- публикация состояния: просто записать
end

local is_hm

function pvp.on_world_update_host()       -- ← считает ТОЛЬКО хост
    if tmr == nil then
        tmr = 60 * ctx.proxy_opt.time_out -- длительность фазы в секундах → в кадры
        is_hm = false
        rpc.update_timer(tmr)             -- сразу опубликовать
    else
        tmr = tmr - 1
        if tmr == 0 then
            rpc.timer_ended(is_hm)        -- событие: фаза кончилась
            tmr = nil
        elseif GameGetFrameNum() % 20 == 14 then
            rpc.update_timer(tmr)         -- ← и публиковать повторно каждые 20 кадров
        end
    end
end

function pvp.on_world_update()            -- ← выполняется у ВСЕХ
    GuiStartFrame(gui)
    GuiText(gui, 128, 0, math.ceil(time / 60))
end
```

Что здесь стоит забрать в M3:

1. **Единицы — кадры.** `60 * секунды`, а на экран выводится `math.ceil(time / 60)`. Так счётчик
   не зависит от реального fps.
2. **Роли жёстко разделены:** отсчёт — в `on_world_update_host`, отрисовка — в `on_world_update`.
   Клиент про время ничего не решает, он только получает `time`.
3. **Периодическая публикация — каждые 20 кадров**, `opts_reliable`, плюс немедленная публикация в
   начале фазы. Именно это делает состояние устойчивым к потере пакетов.

### Одна ошибка EW, которую повторять не надо

`rpc.timer_ended(is_hm)` — **одноразовое событие**, и после него хост обнуляет `tmr`. Если это
сообщение потеряется, у клиента фаза не переключится, а состояние (`time`) уже перестанет
публиковаться. Правильнее выводить переключение фазы **из состояния**: публиковать не только
оставшееся время, но и номер/имя фазы, и на клиенте переключаться, когда пришло новое значение.
Тогда потеря события самоисправляется следующей же публикацией.

## 4. Состояние матча: что в нём лежит

Минимальный набор на M3:

| поле | смысл | владелец |
| --- | --- | --- |
| `phase` | `lobby` / `drop` / `play` / `results` | хост |
| `time_left` | кадров до конца фазы (0 = без ограничения) | хост |
| `alive` | сколько игроков ещё в игре | хост (считает по ростеру) |
| `match_id` | номер матча; растёт при рестарте | хост |

**Как публиковать.** Два варианта:

- **`rpc:create_var("match", cb)`** — готовая синхронизируемая переменная: `var.set(v)` публикует,
  `var.values[peer_id]` хранит последнее значение от каждого пира, а повторная публикация делается
  автоматически на `on_should_send_updates`. Важно: этот хук срабатывает на **подключениях**, а не
  периодически, — то есть изменения и входы покрыты, а для устойчивости к потерям периодическую
  публикацию всё равно надо добавить самой (как EW делает `% 20`).
- **Свой `rpc.match_state(tbl)`** с `opts_reliable` и публикацией по таймеру — то же самое, но
  полностью под твоим контролем и с полем `frame` для точной метки ([docs/02](02-multiplayer-entangled-worlds.md), §4.3).

Для M3 бери второе: состояние будет расти (зона, счёт, результаты), и лучше сразу иметь одну
понятную точку публикации.

**Читать состояние надо у хоста:** `match.values[ctx.host_id]`, а не своё.

## 5. HUD: как рисовать

Ванильный API (проверено по `tools_modding/luacheck_config.lua`, строки 292-332):

```lua
local gui = GuiCreate()                        -- один раз, на уровне файла
...
GuiStartFrame(gui)                             -- начать кадр
GuiText(gui, x, y, "текст")                    -- нарисовать строку
GuiTextCentered(gui, x, y, "текст")
GuiGetScreenDimensions()                       -- размеры экрана, если нужны координаты
GuiColorSetForNextWidget(r, g, b, a)           -- цвет следующего виджета
```

**Развилка, на которую стоит обратить внимание.** В ванильном примере
`data/scripts/_examples/credits.lua:120-130` `GuiStartFrame(gui)` вызывается **каждый кадр**, а в EW
(`pvp.lua:640`) — **один раз** при старте фазы. Начни с варианта «каждый кадр» (как в ванили) — он
точно рабочий; если увидишь артефакты или лишние наложения, посмотри, как выкручивается EW.

**Что рисуем в M3:** строку вида `ФАЗА 2:31 · живых 3` в углу экрана. Начать можно с одного
`GuiText` — этого уже достаточно, чтобы «геймплей появился».

## 6. Первый шаг, который даёт видимый результат

Порядок, при котором ты быстро увидишь что-то на экране, а не очередной лог:

1. В `module.lua` — `local gui = GuiCreate()`.
2. Локальное состояние: `phase = "play"`, `time_left = 60 * 180` (3 минуты).
3. В `on_world_update_host` — уменьшать `time_left`, публиковать раз в 20 кадров.
4. В `on_world_update` — `GuiStartFrame(gui)` + `GuiText(...)` со фазой, временем и числом живых.
5. Переходы фаз пока просто `GamePrint` + строка в лог.

**Что уже проверяется в одиночку** (хоть друга и нет):
- HUD рисуется и не мешает игре;
- таймер тикает и доходит до нуля;
- переход фазы логируется;
- ничего не падает при спавне/смерти/паузе.

**Что без второго игрока не проверить:** совпадает ли таймер у двух машин, переживает ли он потерю
пакетов, как ведёт себя при выходе игрока в середине матча.

## 7. Открытые решения (за тобой)

- **Длительности фаз** — сколько длится drop и play, есть ли prep-фаза (это уже M4).
- **Что такое Lobby в нашей терминологии**: отдельное состояние или «до спавна игрока». У EW
  лобби живёт в прокси, а не в игре.
- **Условие конца**: последний выживший (зависит от M6/M7) или таймер + счёт.
- **Политика дисконнекта в матче** — прямо влияет на «число живых» ([docs/02](02-multiplayer-entangled-worlds.md), §15.4).
- **Пауза.** `on_world_update` не вызывается на паузе — HUD в этот момент просто не перерисуется.
  Если это мешает (например, хочется видеть таймер в инвентаре) — нужен `OnPausePreUpdate`.
